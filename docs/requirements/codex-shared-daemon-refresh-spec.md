# 需求规格：跨平台模型选择与 Codex 共享后台服务确认刷新

## Problem Statement

用户已经在 GPTEasy 中应用供应商配置，磁盘上的 Codex 模型元数据目录也可能已经具备通用四档，但驻留的 Codex 共享后台服务仍可能使用旧目录。退出 CLI、重新打开终端或看到配置写入成功，都不能证明共享后台服务已经刷新。现有待重启提示主要面向 ChatGPT/Codex 桌面版与 Codex CLI，难以解释“配置已保存，但模型或思考强度菜单仍未变化”，也不能可靠区分写入失败、后台刷新失败和供应商服务端问题。

同时，WSL2 桌面切换、WSL2 内 Linux 脚本及独立 Linux 的 Bash/Zsh 切换尚未提供与 Windows 一致的完整当前供应商目录。只补重启提示、只写默认模型或只证明 JSON 能生成，均不能满足跨平台模型与思考强度选择需求。

这项需求较大，必须先形成具有安全边界、失败语义、验收依据和阶段退出条件的规格，再逐阶段实现；不能把已有的通用四档代码当作完整交付，也不能在一次大改后才发现共同管理、恢复或实例刷新遗漏。

## Solution

提供一条可解释、可恢复的跨平台流程：从有效的模型目录快照生成当前供应商的完整 Codex 模型元数据目录；用户明确操作后安全提交配置与目录；分开展示磁盘提交和运行实例刷新结果；Windows 对可信的 Codex 共享后台服务提供独立预览与二次确认重启；WSL2/Linux 提供完整目录、共同管理和明确的人工刷新路径。

所有已发现模型均提供 `low`、`medium`、`high`、`xhigh`，目录默认 `high`，无需逐模型 profile。这是客户端兼容策略，不是供应商能力认证。最终分别验收目录/schema、配置与恢复、运行实例生命周期、真实 Codex 菜单，不以其中一项代替另一项。

实现按本规格末尾的阶段计划推进，最终生成未发布的 Windows NSIS 测试安装包，由用户人工测试。中间阶段必须标明能力边界；WSL/Linux 目录和真实菜单不是可选后续项。

## User Stories

1. 作为主要用户，我希望应用供应商后看到当前供应商的全部发现模型，以便选择非默认模型，而不是只能使用默认模型。
2. 作为主要用户，我希望每个模型都能选择四档思考强度，以便不必逐模型维护 profile 或手工修改目录。
3. 作为主要用户，我希望新模型和未知模型也使用相同选择器策略，以便不因模型名称未被 GPTEasy 识别而失去选项。
4. 作为主要用户，我希望目录默认档位为 `high`，以便在未作显式选择时采用一致的兼容默认值。
5. 作为主要用户，我希望知道目录档位只是兼容声明，以便不会把菜单可选误认为供应商已通过四档真实请求验证。
6. 作为主要用户，我希望根级实际推理强度与目录可选档位分别处理，以便既有官方映射不会错误收窄模型选择器。
7. 作为主要用户，我希望切换供应商时只看到当前供应商的模型，以便不会将其他供应商的模型与当前路由混用。
8. 作为主要用户，我希望两个供应商存在同名模型时仍正确切换路由，以便模型名称相同不会造成供应商身份混淆。
9. 作为主要用户，我希望模型目录快照缺失、损坏或验证绑定失效时收到可处理的错误，以便重新验证，而不是静默得到只有默认模型的目录。
10. 作为主要用户，我希望重新验证失败后保留上一份有效快照，以便失败不会破坏已有可用配置。
11. 作为主要用户，我希望重新验证可以修复缺失或损坏的快照，以便严格的应用校验不会使供应商永久无法恢复。
12. 作为主要用户，我希望看到配置已保存与后台服务待刷新是不同结果，以便不会因为菜单尚未变化而重复覆盖配置。
13. 作为主要用户，我希望分别看到桌面版、CLI 和共享后台服务的待处理状态，以便知道应该处理哪个运行实例。
14. 作为主要用户，我希望退出 CLI 后仍驻留的共享后台服务保持待刷新提示，以便重新打开终端不会被误认为已经刷新。
15. 作为主要用户，我希望页面刷新和应用启动只检查状态，以便不会意外启动、升级或重启后台服务。
16. 作为主要用户，我希望在后台服务管理接口不受支持时看到明确限制，以便可以人工处理，而不是被错误告知服务已停止。
17. 作为主要用户，我希望了解所选管理入口的来源以及与终端默认入口的差异，以便多套 Codex 安装不会导致难以解释的行为。
18. 作为主要用户，我希望多个可信入口无法自动解歧时只选择后端发现的候选，以便无需粘贴路径或执行任意命令。
19. 作为主要用户，我希望看到已知 CLI、受管程序和运行中服务版本，以便区分入口差异、版本差异与配置未刷新。
20. 作为主要用户，我希望版本缺失或版本不同不会自动触发升级，以便重启只改变实例生命周期。
21. 作为主要用户，我希望主动选择重启后台服务并看到影响预览，以便先结束需要保留的 Codex 任务。
22. 作为主要用户，我希望后台服务重启要求独立的第二次确认，以便配置应用或强制设置确认不会隐含任务中断授权。
23. 作为主要用户，我希望取消或稍后处理时仍保存新配置与待刷新证据，以便稍后继续，而不必重新应用供应商。
24. 作为主要用户，我希望重启前身份或配置发生变化时预览失效，以便不会对过期目标执行危险操作。
25. 作为主要用户，我希望可靠确认停止的服务不会为完成刷新而被启动，以便 GPTEasy 不创建不需要的运行实例。
26. 作为主要用户，我希望重启结果依据旧实例退出和新实例可信运行核验，以便命令退出码为零不会冒充实际成功。
27. 作为主要用户，我希望重启失败后保留已经提交的新配置，以便后续新启动的 Codex 仍能读取完整配置。
28. 作为主要用户，我希望超时或执行中断后先重新检查且不自动重试，以便不会重复中断可能已经重启的服务。
29. 作为主要用户，我希望人工重启或服务自然停止后可以只读协调状态，以便不必再次由 GPTEasy 执行重启。
30. 作为主要用户，我希望后台服务刷新成功后仍保留旧桌面版和旧 CLI 的待重启项，以便不会误以为所有消费者均已刷新。
31. 作为主要用户，我希望目录兼容修复也生成待刷新证据，以便配置正文未变时，驻留服务仍被正确提示。
32. 作为主要用户，我希望供应商应用、保存并应用、登录模式切换和恢复配置采用一致的刷新规则，以便不同入口不会遗漏旧实例。
33. 作为主要用户，我希望工件没有变化时不制造新的待刷新代次，以便仅改名称或重复无变化操作不会覆盖已有证据。
34. 作为主要用户，我希望强制设置前创建完整恢复点并复读校验配置与目录，以便损坏旧配置时也能安全重建。
35. 作为主要用户，我希望强制设置分开报告本地提交与后台刷新结果，以便本地成功不会因为后续刷新失败而被误报为重建失败。
36. 作为主要用户，我希望提交失败时恢复经过校验的旧状态，以便不会留下半成品目录或悬空指针。
37. 作为主要用户，我希望操作中崩溃后依据旧/新修订恢复状态，以便不会因未收到 UI 成功消息而盲目回滚或重复重启。
38. 作为主要用户，我希望外部修改造成歧义时停止自动处理，以便 GPTEasy 不覆盖其他工具或用户的新状态。
39. 作为 WSL2 用户，我希望桌面供应商切换生成完整 Linux 模型目录，以便在发行版内选择非默认模型和四档思考强度。
40. 作为 WSL2 用户，我希望桌面与 Bash/Zsh 识别、切换和恢复对方的新目录协议，以便共同管理不会丢失目录字段。
41. 作为 WSL2 用户，我希望普通检查不启动已停止的发行版，也不运行 guest 探针，以便状态查看保持无启动副作用。
42. 作为 WSL2 用户，我希望明确操作临时启动后只等待自然停止，以便发行版或 Codex 任务不会被强制终止。
43. 作为 WSL2 用户，我希望各发行版、用户和 Codex home 独立协调，以便一个目标的刷新不会清除另一个目标的待处理状态。
44. 作为 WSL2 用户，我希望 Windows 互操作入口不会被当作 Linux CLI，以便不会用宿主程序错误管理 guest 环境。
45. 作为 Linux 脚本用户，我希望导出物离线携带每个供应商的完整目录，以便目标机不需要网络、Python、Node、jq 或 GPTEasy 可执行文件。
46. 作为 Linux 脚本用户，我希望 source 只定义函数和常量，以便不会写入配置、探测 Codex 或启动服务。
47. 作为 Linux 脚本用户，我希望改动默认模型或关键组合后陈旧载荷被拒绝，以便手工维护供应商表时不会写入不匹配的目录。
48. 作为 Linux 脚本用户，我希望重新验证后明确重新导出才能更新模型，以便不会把离线快照误认为实时同步。
49. 作为 Linux 脚本用户，我希望目录先完整就绪，再原子切换配置引用，以便中断最多留下未引用的完整文件。
50. 作为 Linux 脚本用户，我希望旧目录不可变且恢复时复用旧引用，以便切换不会破坏已有恢复点。
51. 作为 Linux 脚本用户，我希望恢复所需目录缺失时停止并说明，以便 restore 不生成悬空指针。
52. 作为 Linux 脚本用户，我希望空格、非 ASCII home、自定义 Codex home 和受支持的配置 symlink 正确处理，以便目录始终属于本次明确目标环境。
53. 作为 Linux 脚本用户，我希望成功切换和恢复后都提示运行实例可能仍使用旧配置，以便不会把磁盘结果误认为菜单已加载。
54. 作为 Linux 脚本用户，我希望缺少 daemon 管理接口时仍可写入兼容目录，以便菜单支持不被不必要的后台控制能力阻断。
55. 作为 Linux 脚本用户，我希望 CLI 本身不支持完整目录 schema 时在提交前停止，以便不会静默去掉目录或自动升级。
56. 作为主要用户，我希望诊断区分目录、提交、刷新、旧会话显式设置和服务端路由问题，以便不会使用强制设置修复不属于本地的错误。
57. 作为主要用户，我希望问题日志不包含 API Key、地址、完整命令行或未脱敏模型 ID，以便可以安全提供排查证据。
58. 作为维护者，我希望每个实施阶段都有可观察的退出条件和回归测试，以便可以一步一步实现而不是依靠内部函数测试推断完成。
59. 作为人工测试者，我希望收到未发布的安装包、校验值和测试清单，以便明确哪些自动结果已验证、哪些真实菜单仍需人工验证。
60. 作为维护者，我希望没有执行的真实 Windows、WSL2 或 Linux 验收保持未验收状态，以便不会以构建成功或隔离 App Server 解析代替完整交付证据。

## Implementation Decisions

### D1. 沿用领域边界，不将生命周期对象混合

分别建模 ChatGPT/Codex 桌面版、交互式 Codex CLI、Codex 共享后台服务、GPTEasy 会话服务进程和身份不明的其他 App Server。共享后台服务是现有待重启协调中的独立服务项，不进入桌面进程树结束集合，不被当作普通 CLI，不与应用自有服务合并。

配置修改与生命周期控制继续分离。Windows 第一阶段主动控制仅限已验证的 `pid` backend、当前 Windows 用户默认 Codex home。自定义 home、其他用户、环境不匹配和未经验证 backend 均不得主动重启。WSL/Linux 主动服务控制不属于本规格，但完整目录及人工刷新流程属于必做范围。

### D2. 严格模型目录快照与共享生成规则

供应商应用、目录修复、WSL 写入和 Linux 导出必须使用与供应商验证指纹绑定的有效模型目录快照。缺失、损坏、无法识别或绑定失效在写入或导出提交前失败，不允许空集合回退、仅补默认模型掩盖快照故障。保持重新验证能够修复快照，不把严格应用校验错误地放到必须先加载损坏快照的恢复前置条件上。

各平台复用同一完整 Codex schema、模型规范化/去重和默认模型存在性规则，只输出当前供应商发现模型并确保默认模型存在。采用 `common-reasoning-selector-v1`：每条目四档，默认 `high`，保留未知能力描述及已有图片输入兼容策略，不由模型名称推断已验证能力。不要求新增结构化能力快照或逐模型 profile。

根级 `model_reasoning_effort` 继续采用既有官方映射：已确认 OpenAI/DeepSeek 映射保持 `high`，未映射供应商省略根级字段。目录默认值不是新的官方映射。旧根级 `none` 仅在用户明确应用时按既有受管迁移处理；启动、source 与只读检查不改写它。已有会话的显式模型/effort 不由本功能强制覆盖。

### D3. 离线载荷及绑定校验

Linux 导出由 Rust 预生成每个供应商的完整 JSON 载荷，携带生成协议、策略、供应商身份、默认模型/模型集合与关键组合的绑定信息，以及载荷字节 SHA-256 摘要。使用不执行文本的安全载荷封装，分别防护 JSON、shell 字符串和 here-document 边界。模型、名称、描述与地址不能成为代码或路径。

明确切换时使用已有 SHA-256 工具核验载荷及绑定，不能核验即失败关闭；不使用正则重建任意 JSON，不使用 eval 或网络请求补全。摘要是离线数据完整性依据，不替代供应商验证，也不新增 shell 跨操作已应用证据或持久化哈希状态机。

保留供应商表可维护性，但修改默认模型、模型集合或服务地址/API Key 等关键组合时必须同步重新生成载荷与绑定；否则拒绝切换并提示重新验证/重新导出。仅显示名称变化不改变模型集合。导出始终代表导出时的快照，重新验证不自动更新旧导出物。

### D4. 不可变 Linux 目录与唯一活动指针

WSL/Linux 将目录放在本次实际目标 Codex home 的私有受管目录中，使用受控来源 ID 与不透明工件 ID，不使用模型 ID、供应商名称或地址构造路径。每份已提交目录不可变，新版本另建文件；目录不含 API Key，不接受 symlink/hardlink 替代，沿用私有权限、所有权和文件身份校验。

配置仅包含一个根级 `model_catalog_json`，以正确 TOML 转义的 Linux 绝对路径引用已完整提交的目录。目录所在 home 不随当前工作目录或配置 symlink 的目标悄悄改变，不使用 Windows 宿主路径。外部目录不接管、不覆写、不删除。第一版可不自动清理目录；未来清理也必须在共享锁内保留当前配置、双方恢复点/桌面备份及有效操作的全部引用，不能按年龄删除或用删除旧目录迫使服务刷新。

### D5. Linux 配置提交与恢复

一次切换在现有共享锁内完成目标/CLI/载荷校验、完整恢复点、不可变目录提交、完整配置候选生成、并发及 symlink 身份复核、原子配置替换和复读。配置替换是活动目录切换的提交点。独立 Linux 延续整体生成最小可用配置的规则，不拼接或迁就损坏旧 TOML；旧配置保存在恢复点。凭据仍使用既有独立的命令式工件协议。

目录未就绪不能提交配置指针。目录成功而配置失败时保留旧配置与旧目录，允许暂留未引用的完整文件。配置已提交但进程中断时，不以未打印成功为依据盲目覆盖新配置。

restore 恢复旧配置、原存在性和旧指针前，须核验所需受管目录仍存在且有效；缺失时停止，不写入悬空指针。原配置没有目录引用或原来没有配置文件时正确恢复，不强补目录。保持恢复确认、完整恢复点、配置 symlink、备份所有权及覆盖警告等现有行为。

### D6. WSL 桌面与 Bash/Zsh 同步升级共同管理协议

采用 schema v2，共同表达目录受管引用、生成策略/协议与根级绝对引用，二者必须对应同一工件。桌面 writer/reader 与 Bash/Zsh 必须同时理解，能识别、切换和恢复另一方创建的有效状态；不能把单方升级当作共同管理完成。

schema v1 与受支持旧格式只读兼容，不自动迁移；下次明确应用在备份与共享锁保护下迁移。未知格式按适用入口规则处理：桌面/状态读取形成冲突，独立 Linux 明确整体替换仍遵守其已有授权。旧脚本不能声称获得新能力；遇到新格式沿旧规则处理，需要重新导出。

只读协调区分供应商关键组合更新、目录快照差异、目录缺失/损坏、目录策略旧版和运行实例待刷新。物理路径与来源 ID 差异不等于供应商变化；不自动替换较旧脚本的目录或恢复已删除的供应商。

WSL 桌面继续使用 Windows SQLite Saga，共享锁覆盖 guest 读取、写入复读和状态提交；shell 不复制 SQLite Saga 或跨崩溃状态机。目录引用、修订和待刷新证据进入已有桌面恢复边界。

### D7. WSL 生命周期与 Linux 兼容性门禁

目标按发行版注册身份、Linux 用户及 Codex home 隔离；脚本支持实际选择的自定义 home，桌面 WSL 仍管理默认用户默认 home。拒绝将 Windows 互操作入口作为 Linux CLI，不能凭命令存在或版本字符串推断目录/daemon 能力。

普通 list/inspect 对 Stopped 发行版零 guest 调用、零启动、零 Codex 探针，仅展示最后观察与待核验。明确刷新实际状态、核验或切换才可临时启动。完成后释放锁、退出自有 guest 进程，最多等待自然停止 10 秒，不终止发行版或用户负载。发行版实际停止可协调其旧实例项，但不证明下次菜单已验收。

Linux 目录/schema 契约须单独验证。CLI 本身不支持完整目录时提交前停止，不静默省略目录或自动升级；仅缺 daemon 管理接口不阻断兼容目录写入。Running 发行版提交后保守提示待重启，缺少 guest 可信检测时不声称“已检测到服务”。

### D8. 可信 Windows CLI 发现与服务检测

独立后端服务负责检查、预览、确认执行和核验。枚举桌面附带、npm 和可信独立安装，解析启动脚本与最终程序身份，区分终端默认入口和所选管理入口。不只取 PATH 首个，不将 where.exe 当作完整 PowerShell 解析，不执行用户 alias/function 或任意脚本，不永久硬编码用户安装目录。

仅执行后端核验的绝对入口和固定参数。自动只读探针须先在对应安装方式/版本验证无启动、安装或更新副作用。以实际支持能力而非固定版本号选择入口；缺失版本字段单独显示未知，不因此凭空判定身份可信或不可信。多个候选无法解歧时，前端只能选择后端候选 ID。

将管理状态报告与实际进程交叉核验：默认 home、backend、PID、创建时间、规范化可执行路径、当前用户归属、有限 daemon 命令身份和属于目标环境的 socket/control 位置。不能只凭名称、app-server 参数或目录前缀认领，不能执行响应返回的任意路径。严格排除应用自有服务、桌面 bundled App Server 和身份不明的其他工具。

未知 backend、缺入口、不支持命令、超时、损坏 JSON 或身份矛盾降级为 unknown/unsupported，不能当作 stopped；无 CLI 窗口不等于服务空闲。

### D9. 两个状态维度与既有待重启聚合

运行状态为 `running / stopped / unknown / unsupported`；针对某次已提交变更的刷新状态为 `not_required / pending / restarting / refreshed / failed / indeterminate`。`refreshed` 只表示实例生命周期核验通过，不表示真实请求、菜单或全部会话设置已通过。

扩展已有持久化待重启上下文，记录上下文版本、环境、变更代次、目标配置/目录修订、提交时点、已观察服务身份、检测不确定性及最后刷新结果；不复制凭据、目录正文或完整命令行，不增加独立全局“已生效”布尔值。

全局 `pendingRestart` 聚合桌面、CLI、服务项及无法可靠排除的旧实例。服务成功只清对应服务项。旧记录按既有消费者规则兼容，并只读补充检测；创建时点早于已知提交时点时保守待刷新，证据不足时无法确认；没有历史变更证据时不捏造历史代次。

### D10. 变更触发与可恢复证据

应用/重新应用供应商、当前供应商保存并应用、强制设置、登录模式切换、恢复配置及目录兼容修复，在相关工件实际变化时产生待刷新代次。仅改显示名称、验证未保存、取消、完全无变化或完整回滚不产生错误代次，并保留或恢复原上下文。启动/页面刷新仅只读协调；外部修改按既有冲突规则处理。

写入前及提交前后检测，捕获期间出现的服务；时间无法可靠比较时保守保留待刷新。完整环境操作沿用 Saga，目录兼容修复仍只接受严格匹配历史 GPTEasy 模板的受管目录，不把外部或人工能力声明当作旧模板。目录单独修复也必须持久化变更意图、旧/新目录修订与待刷新证据，覆盖目录提交到状态提交之间的崩溃窗口。

恢复按旧/新/第三种修订收敛：已提交补齐待刷新；已回滚保留原上下文；第三种进入冲突/indeterminate，不覆盖外部状态。服务执行中断后先重新核验，不重复可能已经发生的 restart。

### D11. 强制设置的两阶段结果

强制设置仍需已验证供应商、重新验证/修订门禁、首次配置重建确认和完整恢复点，不能接收前端任意路径、正文、目录或命令。先提交并复读校验 provider、默认模型、凭据引用、完整目录与指针，再产生同一环境的刷新预览，第二次确认才可重启。

结果至少区分：`completed`（本地提交及实例核验完成，或可靠确认无旧实例需刷新）、`completed_with_refresh_pending`（本地成功但未获确认、缺能力、刷新失败或仍可能有旧实例）、`failed_and_restored`（本地提交失败且旧状态已复读恢复）、`indeterminate`（重启、修订或身份无法判断）。只有确实核验恢复成功才报告 restored，否则保留不确定结果与人工处理依据。

本地提交成功后，刷新失败、取消、unsupported 或不确定均不得回滚新配置，也不误报为供应商验证失败。提交失败/恢复点失败/候选不完整/写后不一致时不执行 daemon 操作，依恢复证据保全旧状态。服务端错误分组与旧会话显式设置单独诊断，不由本地强制设置改写服务端路由或凭据。

### D12. 绑定预览、独立确认与受控执行

前端只传后端生成的短期预览 ID，必要时传后端候选 ID，不传路径、PID 集合、附加参数或命令。预览绑定环境/home、变更代次、配置/目录修订、可信 CLI 入口及最终程序身份、daemon 身份；换代、PID 复用、入口替换、再应用配置或过期均拒绝执行，要求重新检查与确认。

执行与供应商、模式、恢复和目录修复共用协调锁；持锁复核绑定，用同一核验入口调用固定 daemon restart，隐藏 Windows 窗口、使用管道、限制时限与输出。没有配置提交授权不能顺带改配置，没有重启确认不能执行；绝不调用 update、切 CLI 包、结束用户 CLI、直接杀服务 PID 或重建包目录。

可靠停止时只协调旧实例退出，不为完成操作而启动。执行后核验旧身份退出、新身份可信运行、创建在目标提交之后、工件修订和代次未变，再只清目标服务项。命令退出码不替代核验。外部修改导致 revision 不一致时不宣告旧目标刷新成功。

### D13. 失败、超时与重新检查

命令失败且旧实例仍运行，或旧实例退出但新实例未启动，记录失败并保留新配置/待刷新，提供人工恢复，不自动重复 restart。超时、响应损坏、应用执行中退出和无法辨别旧/新身份为 indeterminate；即使回收自有命令进程，也不推断服务操作已取消。

重新检查依据实际旧/新实例、目标工件与提交证据收敛，可能确认刷新、确认旧实例仍待处理，或继续不确定。只能在结果重新确认、生成新预览且用户再次确认后考虑新操作。人工重启与自然停止通过只读协调，不制造生命周期操作。

### D14. UI 与人工刷新说明

环境区域显示共享后台服务运行状态、刷新状态、已知版本、入口来源/差异、重新检查和可用的独立重启入口。文案明确“配置已保存，后台服务仍可能使用旧配置；重新打开终端不一定刷新”。确认明确任务中断风险，稍后/关闭保留证据。

强制设置先显示本地已保存或已恢复，再显示已刷新/待刷新/失败/不确定，不能用一个布尔成功覆盖两者。服务重启成功但旧 CLI/桌面仍在时继续显示其待重启；不宣称真实菜单或供应商请求已验收。版本不同只说明重启不升级。

WSL/Linux 切换、恢复及清理警告统一区分磁盘结果和可能未刷新的实例。人工命令仅在目标原生 Linux CLI 与对应管理契约已核验时展示，并说明用户及目标 home；否则给该安装适用的人工处理限制，不无条件推荐裸 codex、Windows 入口、sudo 或 update。source 零探针/写入/网络，codex-full 不增加隐式重启或固定 no-daemon。

### D15. 最小脱敏诊断

复用问题日志，记录检测、准备、工件提交、预览、执行、核验、协调与恢复等阶段及变更来源；补充策略/schema、模型数量、默认模型存在性、指针有效性、入口来源/候选数/能力分支、可信身份结果、已知版本、有限错误码、旧/新实例信息和是否仍有其他待处理消费者。

路径和代次按现有规则脱敏，能力检查明确 not_checked/matched/mismatched/unsupported。严禁 API Key、认证/配置正文、目录正文、完整命令行、供应商地址、请求内容、未脱敏模型 ID，以及未筛选管理 stdout/stderr 进入日志。新增日志同时补阶段区分与敏感字段排除测试。

### D16. 决策衔接与增量实现

本规格按 ADR-0054 提案组织新增范围，同时保持既有直接配置、用户确认、桌面控制、自有服务隔离、SQLite Saga、共同管理、shell 最小状态和 WSL 安全生命周期约束。进入实现时明确记录对既有 WSL 工件协议和通用四档平台范围的扩展，不让 proposed 文档默默覆盖 accepted 决策。

保留当前未提交的通用四档基础与严格历史模板修复兼容，不要求为写规格回滚代码。后续如需撤销某段试验，只针对可辨认的本任务改动，不使用整体工作区回退。具体数据库迁移、载荷封装和模块物理划分在相应阶段选择，不提前把未经验证的外部命令契约固化。

## Testing Decisions

### 测试切面

优先复用最高层、稳定的用户用例入口：环境应用/检查/恢复及持久化状态、WSL 应用与实际 guest writer/reader harness、导出后实际 Bash/Zsh 用户命令。三种产品入口共享一套外部行为验收规则，不为了“只有一个测试入口”而新增通用执行框架。

Windows 共享后台服务仅增加一个聚合的外部运行时边界，封装可信入口发现、受限命令执行、进程身份读取与时间，使高层环境流程能模拟可信服务驻留、换代、超时和身份不确定。参考现有消费者扫描、桌面控制边界和故障注入模式，不按每个内部函数增加 mock。

好的测试断言可观察结果：磁盘工件与引用、恢复点、持久化代次、环境快照、允许/拒绝的操作、实际外部命令参数与次数、无副作用、UI 用户行为和脱敏日志；不绑定内部调用顺序、私有方法名称或模块拆分。真实菜单保持独立人工验收。

这一测试切面已向用户提出供核对；未收到反馈不写成“用户已确认”。如有调整，更新本节而不扩大控制范围。

### 既有测试先例与回归门禁

- 环境 workflow 的临时 Codex home、SQLite 实际状态、故障注入与恢复测试，作为 Windows 持久化及强制设置测试先例。
- 消费者检测与桌面应用测试中的可信身份、运行时边界和时钟，作为服务检测/换代先例，不复用桌面终止能力管理 daemon。
- WSL guest harness 与现有 Bash/Zsh 导出执行、共同管理、备份和 Linux/WSL 验收门禁，作为跨平台协议先例；补齐测试 fixture 的有效快照，不为通过旧 fixture 放松生产校验。
- 前端现有 Tauri invoke mock 与 Testing Library 用户交互测试，覆盖初次确认不执行 restart、独立第二次确认、取消和结果分别显示。

### 人工验收与完成判据

1. Windows：真实默认共享服务先加载旧目录；通过 GPTEasy 提交新目录，保持待刷新；独立确认重启，核验新身份且版本未自动升级；真实 CLI 的 `/model` 可选非默认模型并进入四档。保留旧 CLI/桌面项，另测人工重启、超时不重试和强制设置分支。
2. WSL2 桌面：真实 Linux CLI 读取 v2 目录，默认/非默认模型可选并有四档；与脚本交替切换和恢复一致，Stopped 与临时启动无强制终止。
3. WSL2 脚本：Bash 和 Zsh 分别提供真实模型/四档证据、桌面互操作和 restore 证据。
4. 独立 Linux：Bash 和 Zsh 分别提供离线完整目录、真实模型/四档、切换/restore 与目标 home 证据。
5. 有共享服务的各目标覆盖“旧实例读取旧目录 → 磁盘新目录提交 → 人工或受控刷新 → 实际菜单读取新目录”；无共享服务时覆盖旧 CLI 退出与新 CLI 读取。不支持 daemon 管理时仍验收兼容目录和适用人工流程。
6. Windows 的现有启动包装可作对照，不修改其定义；`--no-daemon` 只在已验证支持时作诊断对照，不能绕过默认服务路径完成验收。
7. 目录/schema、磁盘提交/恢复、实例生命周期、真实菜单分别登记；缺少真实平台证据保持未验收。四档菜单不是四档请求能力验证，不要求本规格新增供应商全模型/四档 API 探测。
8. 完整交付需上述必做平台证据齐备；可以先交付阶段性 Windows 测试安装包，但必须标明跨平台未完成项，不能关闭总需求或宣称完整交付。

## Out of Scope

- 后台服务自动升级、与当前 CLI 对齐、切换/固定 CLI 包或恢复上游生产更新策略。
- 因没有窗口、任务数量或所谓空闲判断而自动重启；配置保存、页面刷新、source、启动或包装函数触发隐式服务操作。
- GPTEasy 启动、终止、重建或自动重开交互式 Codex CLI；按名称批量结束 Codex、直接杀服务 PID 或接管其他 App Server。
- 未核验 backend、其他用户或 Windows 自定义 Codex home 的主动管理，以及提权操作。
- WSL/独立 Linux 产品内主动 daemon 控制、systemd 通用管理、发行版重启/强制终止；这些需另行验证契约并扩展控制 ADR。
- 结构化模型能力 profile 数据源、逐模型用户覆盖、新的 GPTEasy 思考强度编辑页面或将能力未知改为已验证。
- 网络代理、新增启动时模型发现、全模型/四档请求探测、自动改写供应商服务端分组及旧会话显式模型/effort。
- shell 跨操作持久化哈希/Saga/SQLite 状态机、自动改写旧导出物、自动接管或删除外部目录；首版目录垃圾回收也不必实现。
- 正式发布、打 tag、GitHub/Gitee Release 上传和更新清单推进。生成测试安装包不构成发布授权。

### 现有工作区的处理

当前未提交实现已包含 Windows 目录统一四档/default high、旧图片目录 null/空 reasoning 模板的严格修复识别、兼容策略日志与部分回归/opt-in schema 测试。它们作为增量基础保留，不在规格阶段回退。

经本轮核对，仍存在应用快照读取容错退为空列表、WSL 供应商读取不带完整模型快照、Linux 导出缺少完整目录载荷、共同管理仅旧目录协议、目录修复缺少完整待刷新崩溃证据，以及共享后台服务检测/确认控制尚未实现等缺口。现有代码或测试条目存在，不代表本轮已运行或通过。

本轮只整理规格和创建需求工单，不执行后台服务操作、不改功能代码、不生成安装包、不提交代码。后续保留来源不明或用户已有修改；只有辨认出本任务试验改动并确认不再采用时，才做最小范围撤销。
