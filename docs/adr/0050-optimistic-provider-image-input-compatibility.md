# 对自定义供应商模型乐观声明图片输入兼容

GPTEasy 生成的 Codex 模型元数据目录目前把所有自定义供应商模型声明为仅支持文本，导致实际支持图片的模型在请求到达供应商之前就被 Codex 拒绝。项目决定不增加图片能力探测，而是在目录边界采用统一、可预测的乐观兼容声明，让供应商成为图片请求能否执行的最终裁决者。

## 决策

GPTEasy 为当前活动自定义供应商生成的每个模型目录条目都必须包含：

```json
{
  "input_modalities": ["text", "image"],
  "supports_image_detail_original": false
}
```

该规则适用于供应商模型发现列表中的所有模型以及为完整性补入的默认模型，不因供应商、模型名称或模型家族而变化。

`input_modalities` 是 GPTEasy 对 Codex 客户端门禁采用的兼容声明，不是经过验证的模型图片能力证据。它只表示 Codex 应允许图片请求继续发送到当前供应商，不保证供应商或模型最终接受、理解或正确处理图片。

`supports_image_detail_original` 统一为 `false`。GPTEasy 不根据 `GPT`、`Claude`、`Gemini` 或其他名称推断 `detail: original` 支持情况，因为该能力同时取决于模型和自定义供应商的 Responses API 网关。支持图片的模型仍可使用 Codex 的非 original 图片细节模式。

## 范围

本决策只改变 GPTEasy 生成 Codex 模型元数据目录时的图片相关字段：

- 不增加图片能力探测请求；
- 不改变供应商验证的模型发现、Responses 流式响应或工具调用闭环；
- 不增加数据库字段、能力快照或 schema 迁移；
- 不增加供应商表单选项或按模型配置的界面；
- 不维护 GPT 或其他模型家族的 original 白名单；
- 不改变 OpenAI 登录模式，后者不使用 GPTEasy 的自定义供应商目录；
- 不改变其他上下文窗口、推理档位、工具能力等元数据规则。

本决策是 ADR-0049 中“未知模型使用保守兼容模板”的一个明确例外。例外仅限图片输入门禁；其他未知能力仍保持未知或使用原有保守规则。

## 生命周期

实现必须确保新规则通过同一模型目录渲染器进入原生 Codex、WSL2 和独立 Linux 的受管配置流程，并继续服从既有备份、原子写入、Saga、失败恢复和消费者重启要求。

应用升级不得在启动时静默重写用户当前 Codex 配置。新建、切换、更新、恢复或明确重新应用供应商时，才由现有受管配置流程生成新目录。已经处于活动状态且仍使用旧目录的供应商，需要用户明确重新应用后才获得新声明。

## 失败语义

对于实际不支持图片的模型，纯文本请求不受影响；只有包含图片的请求可能由供应商返回不支持图片、请求格式无效或其他上游错误。GPTEasy 和 Codex 不得把目录中的乐观声明描述为“已验证支持图片”。

`no image on clipboard` 不属于模型能力或模型目录故障。资源管理器复制文件可能只提供 `FileDrop`，而没有位图剪贴板格式；该情况继续通过图片路径、支持的拖放方式或从图片应用复制位图处理，不在本决策范围内。

## 实施契约

后续实现会话应完成以下最小改动：

1. 修改 `src-tauri/src/provider/model_catalog.rs`，使 `ModelCatalogEntry.input_modalities` 可以序列化两个值，并对所有条目生成 `["text", "image"]`。
2. 保持所有条目的 `supports_image_detail_original` 为 `false`，不得加入模型名称分支或供应商特例。
3. 保持 `render(models, default_model)` 的输入、模型排序、去重、默认模型补入和其他元数据行为不变。
4. 核对 `src-tauri/src/environment.rs` 中所有模型目录生成入口都继续调用同一渲染器，不复制图片字段规则。
5. 不修改供应商验证回执、SQLite `provider_model_catalog` 表、前端供应商合同或供应商验证进度阶段。
6. 更新面向用户的发布说明，说明图片请求改由上游供应商最终裁决，但不得声称所有模型已经验证支持图片。

## 验收标准

- 模型目录单元测试断言所有已发现模型和补入的默认模型都输出 `input_modalities = ["text", "image"]`。
- 单元测试断言所有条目都输出 `supports_image_detail_original = false`。
- 未识别模型的推理能力、描述、排序和默认模型行为保持原有测试通过。
- 环境工作流测试确认应用供应商后写入的新目录包含统一图片声明，并继续参与备份和失败恢复。
- OpenAI 登录模式的配置和清理行为保持不变。
- 使用真实 Codex 和支持图片的自定义供应商执行路径图片 UAT，确认请求不再被 Codex 本地模型能力门禁拒绝。
- 使用不支持图片的模型执行负向 UAT，确认纯文本仍可用，图片请求的失败来自上游且不会破坏当前配置。
- 位图剪贴板和资源管理器 `FileDrop` 分别测试，不把剪贴板格式错误记录成模型目录回归。

## 结果与取舍

该方案改动小、没有额外验证费用，也能立即解除支持图片模型的本地阻断。代价是目录会对纯文本模型作出乐观声明，使不支持图片的错误从 Codex 本地门禁后移到供应商响应；同时所有模型暂不使用 `detail: original`，即使其中部分模型和供应商实际支持该模式。

如果未来需要准确展示图片能力或启用 original，必须另行决策并引入供应商能力元数据或真实请求链路探测，不能在本规则中逐步加入基于模型名称的猜测。
