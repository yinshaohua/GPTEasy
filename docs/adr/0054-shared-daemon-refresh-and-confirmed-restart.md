# 共享后台服务待刷新与用户确认重启

2026-10-02，本机在模型目录已有通用思考档位时，默认共享后台服务路径仍跳过思考强度菜单；用户重启同一 0.157.1 服务后恢复。提议把 Codex 共享后台服务建模为独立生命周期对象，将它的待刷新证据纳入现有待重启协调，并提供独立的用户确认重启操作，以补足“退出 CLI 不一定退出共享服务”的缺口。用户进一步明确：WSL2 与独立 Linux 同样必须解决模型选择和思考强度选择，不能只增加重启提示。

本提案尚未实现，不取代当前生效的 ADR。Windows 受控后台服务重启可先实施，但完整交付包括 Windows、WSL2 与独立 Linux 的当前供应商模型目录、通用四档选择及运行实例刷新后的真实菜单验收。WSL/Linux 模型目录为必做范围，主动 guest/shell 后台服务控制仍为独立后续扩展。

## 跨平台模型选择

提议将 ADR-0049 的当前供应商模型目录和 ADR-0053 的通用兼容默认值扩展到 WSL/Linux。各平台从有效的模型目录快照复用同一生成器，输出完整 Codex schema，包含当前供应商全部发现模型并确保默认模型存在；每个条目提供 low、medium、high、xhigh，默认 high。OpenAI、DeepSeek、兼容供应商与未知模型都无需逐模型 profile；目录选项不表示真实供应商支持已被验证。根级 effort 继续沿用 ADR-0051 的映射并与选择器默认值分开，不在只读操作中清理用户配置。

Linux 脚本在导出时携带按供应商生成的完整离线目录载荷，用户明确切换时写入目标用户及 Codex home。source 无写入、探针和网络副作用，目标机无需新增 Python、Node 或 jq。缺少有效模型快照、导出载荷绑定失效或目标 CLI 不兼容时在配置提交前停止，不能默默只导出默认模型或省略目录引用；重新验证及重新导出更新模型，不增加启动时 /models 请求。

目录使用目标 Linux home 下的私有不可变文件，配置通过唯一根级 model_catalog_json 引用已就绪的 Linux 路径。先提交完整目录，再原子切换配置引用；恢复点保留旧目录，restore 恢复旧指针，引用不确定时不清理。这个取舍允许 shell 延续 ADR-0029 的操作内核验与恢复点协议，避免为了同步修改两个可变文件而复制桌面 Saga。桌面 WSL 仍将目录引用与待刷新纳入 Windows SQLite Saga。

WSL 桌面与 Bash/Zsh 须共同升级管理区块协议并识别、切换和恢复对方写入的目录，建议采用 schema v2。旧格式只读保留，下一次明确应用时备份迁移；新格式不得只有单方理解。独立 Linux 延续 ADR-0048 的最小配置整体替换，只增加受管目录字段，不拼接旧 TOML。接受本提案时需明确扩展 ADR-0030 的工件/共同管理协议以及 ADR-0053 的平台范围；原有共享锁、shell 不复制持久化状态机及备份所有权规则继续保留。

## 强制设置纳入共享 daemon 刷新

“强制设置”同时受 [ADR-0043](0043-confirmed-controlled-config-rebuild.md) 的受控配置重建和 [ADR-0048](0048-force-standalone-linux-provider-switch.md) 的独立 Linux 整体替换约束。它必须在用户明确确认后，从已验证供应商记录生成完整、可恢复的 Codex 配置；不能接受前端任意路径、文件正文、模型目录或 shell 命令，也不能因为旧配置损坏而跳过配置和目录校验。

本决策将强制设置定义为两个有顺序的结果，而不是一个“已成功”布尔值：

1. **本地配置提交**：已创建恢复点，provider、默认模型、凭据引用和完整模型目录均已写入、复读并通过一致性校验。
2. **共享 daemon 刷新**：本地提交后，针对同一环境、同一 Codex home 和同一可信 CLI 入口生成重启预览；用户再次确认后执行 `app-server daemon restart`，并核验旧/新服务身份及工件修订。

本地配置提交成功但 daemon 重启失败、取消、不支持或结果不明确时，不回滚已验证的新配置；保留新配置、完整目录以及待刷新状态，使后续新启动的 Codex 仍能正常读取。只有备份失败、候选配置或目录未完整提交、并发修改破坏提交条件、恢复点不可用或写后校验失败时，才恢复旧状态，并且不得启动 daemon 或执行 restart。

强制设置的最低可用保证如下：

- 配置语法有效，provider、默认模型、凭据引用和 `model_catalog_json` 指针一致；
- 模型目录已完整写入、可读且不包含凭据，恢复点引用的旧目录仍可用；
- 发生异常时保留一套经过校验的旧配置或新配置，不留下悬空指针、半成品目录或无法恢复的中间状态；
- “本地配置已提交”与“共享 daemon 已刷新”分别展示和记录，不能用命令退出码代替运行实例核验。

强制设置提交后的 daemon 刷新遵循以下边界：

- 可信 daemon 正在运行时，显示可能中断 Codex 任务的影响，并要求独立的重启确认；强制设置确认本身不隐含执行重启。
- daemon 已可靠确认停止时，不为了完成强制设置而启动它；`unknown` 不能当作 stopped，也不能盲目重启。
- restart 超时、响应损坏或 GPTEasy 在执行中退出时，先重新探测旧/新实例和工件修订，禁止自动重试可能已经发生的 restart。
- 不自动升级、不切换 CLI 包、不强制结束用户 CLI，不执行前端传入的命令，也不扫描并杀死任意 `codex.exe`。
- 旧 CLI、桌面版和 GPTEasy 自有会话服务仍是独立生命周期对象；daemon 刷新成功不能清除它们的待处理状态。

强制设置至少要能收敛为以下结果：`completed`（配置和 daemon 刷新均已核验，或已确认没有旧运行实例需要刷新）、`completed_with_refresh_pending`（配置已提交但运行中的 daemon 尚未刷新）、`failed_and_restored`（提交失败且旧状态已恢复）或 `indeterminate`（无法判断重启或外部修改结果）。若操作期间崩溃，下次启动依据恢复点、配置/目录修订和 pending context 收敛；不能因为没有收到 UI 成功响应就盲目回滚或重复重启。

DayWay 等供应商返回错误分组，例如 `GPT-Pro (distributor)`，属于供应商服务端路由或分组配置问题。它不证明本地强制设置失败，也不能由本决策擅自改写服务端分组、凭据或请求代理；本地流程只负责保证已验证的配置、目录和 daemon 刷新结果可区分、可恢复。

## 运行实例刷新

保留 ADR-0016/0041 的配置提交与生命周期操作分离、交互式 CLI 不受 GPTEasy 控制，以及 ADR-0033 的自有会话服务隔离规则。后台服务可以承载用户任务，不能因没有 CLI 窗口就自动重启；配置切换、启动检查、页面刷新均不隐含重启或版本升级。

Windows 受控重启只调用同一默认用户环境的可信 CLI 管理接口，并复核服务身份、目标工件修订和旧/新实例。结果只协调对应服务项，不能清空仍在运行的旧桌面版或 CLI 的待重启状态。配置与目录已提交而刷新失败时保留工件与待处理证据；版本对齐作为后续单独预览和确认的操作。目录兼容修复也必须持久化待刷新与恢复证据。

因此，强制设置不能沿用“写入成功即结束”的旧语义：配置提交后必须产生共享 daemon 的待刷新结果，并把重启预览绑定到本次强制设置的环境、工件 revision、daemon 身份和可信 CLI 入口。重启成功只表示运行实例已换代，不表示供应商真实请求、已有会话显式模型/effort 或服务端分组已经正确；这些仍分别验收和诊断。

WSL/Linux 按发行版、用户及目标 Codex home 隔离，使用目标环境的原生 Linux CLI。当前仍遵循 ADR-0030 的 shell 仅提示人工重启，以及 ADR-0031 的不强制终止发行版；普通检查不启动 Stopped 发行版。主动 guest/shell 服务控制需要另行扩展控制边界。缺少 daemon 管理接口不阻断兼容目录的写入，人工刷新也是有效交付路径；旧 CLI 未退出或旧 daemon 未刷新时不能宣告新菜单已加载。

设计、提交与恢复边界、跨平台验收及实施顺序见 [共享后台服务配置刷新设计](../design/codex-shared-daemon-refresh.md)，特别是第 14 节。完整需求必须有 WSL2 桌面、WSL2 脚本及独立 Linux Bash/Zsh 的真实模型列表与四档菜单证据；Windows 测试通过、目录 JSON 生成成功或 daemon 重启成功均不能单独替代这些验收。
