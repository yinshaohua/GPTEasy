# 模型能力 profile 与宽容未知模型

> 2026-10-02 修订：[ADR-0053](0053-common-reasoning-selector-defaults.md) 已替代本文关于未知模型使用 null/空 reasoning列表、或必须有逐模型 profile才能开放选择器的规则。当前原生目录采用通用四档、默认 high，作为客户端兼容声明；本文其余能力证据分层继续适用。ADR-0052 的高级快照和逐模型覆盖仍为后续探索。

GPTEasy 同时管理供应商模型发现列表、Codex 模型目录和当前默认模型的实际 reasoning effort。三者必须保持边界：发现模型不等于能力已验证，目录能力声明不等于请求参数，根级 effort 不等于选择器范围。

## 决策

- 模型目录快照使用版本化结构化 JSON。快照中的模型 ID 去除首尾空白、丢弃空值并精确去重；发现顺序保留，当前默认模型必须来自本次发现结果并排在第一位。
- 旧版 `string[]` 快照继续兼容读取，所有模型能力标记为未知；损坏快照不得静默转换为空列表。
- 未知模型尽量宽容：可以发现、保存、成为默认模型、切换供应商并进入 Codex 目录。未知只表示能力未知，不表示模型不可用。
- 只有可追溯官方 profile 或用户明确覆盖才能声明 reasoning 档位。不得按模型名、家族名或供应商名推断档位，也不得把未知模型伪造为全部档位。
- 用户覆盖只作用于快照中已经存在的模型，并独立标记为用户声明；撤销覆盖后回到官方 profile 或未知状态。
- 保存接口区分三种 reasoning 更新：未提供表示兼容旧调用的“保持现状”，显式 `null` 表示用户选择“自动”并清除当前默认模型覆盖，字符串表示设置指定档位；切换默认模型时不会把旧模型的覆盖值带到新模型。
- 当前默认模型的实际 effort 按模型级覆盖优先、官方供应商映射其次、未知为空的顺序计算。无可靠映射时不继承前一个模型的 effort。
- 应用启动不静默改写旧配置。只有用户明确应用供应商时，才按新快照规则生成 Codex 目录和根级 effort。

## 结果

未知供应商模型不会因为 GPTEasy 的过度限制而无法使用，但 Codex 仍可以基于自身 fallback 或供应商响应决定最终兼容性。模型切换和重新验证的结果可审计，且 Windows、WSL2 和 Linux 导出共用同一模型级 effort 结果。
