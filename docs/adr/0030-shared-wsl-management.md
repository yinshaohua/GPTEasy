# 桌面与 Linux 脚本共同管理 WSL2

桌面 GPTEasy 与 Linux 导出脚本共同管理同一个 WSL2 发行版环境，而不是把脚本写入视为外部配置。双方使用相同的管理区块、命令式凭据工件和发行版内独占锁；桌面仍保留 Windows SQLite 中的 WSL2 Saga 与旧/新哈希，shell 脚本不复制该持久化状态机。此决策取代 ADR-0027 中 Linux 导出延期、`config.toml + auth.json` 双工件写入和仅依赖 SQLite 展示当前供应商的部分；ADR-0031 另行修正临时启动后的生命周期恢复策略。

共享锁使用带 owner 类型、随机 token、PID、进程启动信息及操作类型的发行版内锁目录。桌面从读取 WSL 实际配置前持有锁，直到 Linux 写入复读和 Windows SQLite 提交完成后才释放；shell 切换或恢复则持有到配置、恢复点和凭据清理全部完成。竞争方立即失败并显示非敏感的持锁信息，不自动等待。桌面崩溃留下的锁只能由桌面 WSL2 Saga 恢复；shell 崩溃留下的失效锁只能由用户运行 `gpteasy unlock`，在进程失效检查和再次确认后删除，活动锁不得解除。

运行中的发行版在用户刷新时只读实际配置和凭据工件并协调 SQLite；已停止发行版的普通探测仍不启动，只显示待核验的最后观察状态，用户明确执行“刷新实际状态”后才允许临时启动并只读协调。

统一管理区块必须包含可识别的 schema 版本、唯一供应商 ID和管理来源 ID，并表达模型、供应商名称、地址、Responses wire API 及命令式凭据配置。未知 schema、重复元数据或无效凭据引用都形成管理冲突，双方不得自动覆盖。

早期桌面 GPTEasy 写入的完整管理区块即使缺少 schema、管理来源 ID并使用 `auth.json`，仍按供应商 ID只读识别为“当前，旧格式”，不在刷新时迁移。只有用户下一次明确切换或重新应用时，取得共享锁的写入方才在备份保护下替换为现行管理区块和命令式凭据；原 `auth.json` 始终不修改、不删除，使恢复旧配置后原凭据路径仍然成立。

双方以供应商 ID表达当前身份，并按解析后的名称、地址、模型及凭据文件内容比较供应商配置；TOML 格式、凭据文件路径和管理来源 ID不同不影响当前身份或配置比较，实际组合不同才显示供应商配置有更新。供应商删除前必须核验所有 WSL2 环境没有使用该 ID，Stopped 环境未经用户允许临时启动核验时阻止删除；旧导出脚本以后重新应用已删除 ID时只形成“当前供应商不在目录中”的实际状态，不恢复目录记录。

共享根目录 `.gpteasy-shell/` 分隔保存凭据、shell 恢复点、桌面备份、临时文件和锁。shell 与桌面只恢复各自创建的备份，但清理凭据前必须扫描当前配置、双方备份和有效桌面锁的引用。桌面在 Running 发行版中观察到 shell 配置变化时保守进入待重启；Stopped 发行版经显式刷新后清除待重启。shell 不检测或控制 Codex 进程，只在成功切换后提示用户自行重启。

Linux Bash/Zsh 导出与实现该共同管理协议所需的桌面刷新、共享锁、命令式凭据和状态协调属于同一交付范围。实现可以分阶段推进，但不能把只有单方理解的中间协议作为已完成的 WSL2 共同管理能力发布。
