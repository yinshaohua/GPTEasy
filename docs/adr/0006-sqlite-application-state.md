# 使用 SQLite 保存应用内部状态

GPTEasy 使用由 Rust 后端独占访问的用户级 SQLite 数据库保存每个供应商的当前已验证版本及明文 API Key、最后一次成功应用的供应商 ID 与配置指纹、至多一个未完成配置操作和必要应用设置，并通过事务保持关联状态一致。数据库不保留供应商历史版本、软删除记录或未验证草稿。React 前端只能通过受控的 Tauri command 访问这些数据；Codex 配置、凭据载体和配置备份继续使用普通文件。

SQLite 是供应商目录、凭据、验证记录和操作恢复信息的权威来源，但不是当前用户 Codex 环境实际状态的唯一真相。`config.toml` 及目标 Codex 版本使用的凭据载体共同决定新启动的 Codex 将读取什么；应用在启动、刷新和每次操作前重新读取并与 SQLite 的最后应用证据协调，不一致时进入外部配置或管理冲突，不能自动用数据库覆盖磁盘。

数据库使用代码内按版本顺序注册且只能追加的 SQL 迁移，启动时在一个事务中执行全部待处理版本。迁移前通过 SQLite Backup API 创建可打开的一致备份并默认保留最近三份；迁移失败时回滚并停止启动，不能清空或自动重建数据库继续运行。旧版 GPTEasy 检测到更高版本 schema 时只读拒绝；每个正式发布过的 schema 保留一个脱敏测试数据库，自动验证升级到最新版。

首个 schema 只表达首个可验收版本实际需要的已验证供应商、当前用户 Codex 环境最后应用证据、单个未完成配置操作和少量应用状态。不为 WSL2、多环境、DayWay、自动更新、多语言或其他延期能力预建空表、预留列或通用键值模型；这些能力以后通过追加迁移引入。

全新安装且没有既有 GPTEasy 数据时可以创建初始数据库；已有安装遇到数据库缺失、损坏、迁移失败或更高版本 schema 时，应用进入恢复错误页并停止普通写入，不创建空库继续运行。用户恢复前保留原数据库文件；恢复自动选择按时间倒序排列的最新有效 SQLite Backup API 一致备份，恢复后重新执行只读校验和领域状态协调，不提供备份浏览器。

SQLite 备份恢复只恢复应用状态，不直接覆盖 Codex 配置或凭据载体。恢复后必须先重新读取磁盘工件：一致时恢复正常，存在未完成操作时按其阶段恢复，出现更新状态、外部配置或管理冲突时保留磁盘并停止写入，等待用户处理。

迁移正确性不依赖 migration digest lock、Git tag 字节审计、PowerShell SQL 词法扫描、GitHub attestation 或多架构签名证据。这些门禁不进入重建后的数据库实现。
