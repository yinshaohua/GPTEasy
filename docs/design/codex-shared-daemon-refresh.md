## 1. 问题与证据边界

2026-10-02 的本机反馈与前序诊断形成以下证据：

| 场景 | 观察结果 | 证据来源 |
| --- | --- | --- |
| 磁盘模型目录已有 low、medium、high、xhigh，默认 high | 不使用 daemon 的 CLI 可以展示思考强度菜单 | 前序真实 PTY 对照测试；本次文档会话未重跑 |
| 默认共享 daemon 启动路径 | 可以选择模型，选择后跳过思考强度菜单 | 用户反馈与前序 PTY 对照测试 |
| 增加危险权限参数，同时使用 --no-daemon | 可以展示思考强度菜单 | 前序对照测试；权限参数不是该现象的充分解释 |
| 用户执行 app-server daemon restart | 思考强度菜单恢复 | 用户明确反馈 |
| 重启后的版本输出 | CLI 0.160.0，managed Codex 与 app-server 均为 0.157.1 | 用户提供的 JSON，前序本机命令检查 |

这些结果支持“运行中的共享后台服务没有刷新模型能力状态”这一工作结论，但不能确定其内部究竟缓存了哪个对象、何时读取目录、是否存在热加载接口。相同的 0.157.1 重启后恢复，不能把版本较旧认定为本次故障的必要原因。CLI 与后台服务的版本差异和配置刷新是两个问题。

ADR-0053 正常生成的目录也包含“供应商已发现模型，能力未识别”描述。因此该文字不构成目录过期的判据，不得仅根据它触发重启或宣告故障。

### 1.1 跨 PC 的命令入口差异

2026-10-02，用户补充另一台 PC 的测试结果。以下为用户提供的终端证据，本次会话没有访问该 PC，也没有重新执行其更新操作。

- 删除 PowerShell 中的 codex function 后，`codex app-server daemon update --from-cli -y` 仍返回 unrecognized subcommand 'update'。
- 同一终端执行 `codex.cmd app-server daemon update --from-cli -y` 成功，报告 installedVersion、runningVersion 均为 0.160.0。更新输出明确表示会自动重启运行中的服务，并固定当前 CLI 包。
- 本机 `where.exe codex` 只列出 npm 全局目录中的 codex、codex.cmd；另一台 PC 在它们之前还列出桌面安装目录的 codex.exe。

脱敏后的候选顺序如下：

| PC | where.exe codex 的候选顺序 |
| --- | --- |
| 本机 | `<npm-global>/codex` → `<npm-global>/codex.cmd` |
| 另一台 PC | `<user>/AppData/Local/Programs/OpenAI/Codex/bin/codex.exe` → `<npm-global>/codex` → `<npm-global>/codex.cmd` |

这解释了“移除 function 后仍然出现不同管理能力”的高概率原因：裸 codex 命中了桌面安装目录的可执行入口，而 codex.cmd 命中了 npm 包入口。最终 PowerShell 解析仍须以 `Get-Command codex -All`、`Get-Command codex.cmd -All` 和各实际入口的版本、帮助为准；where.exe 不完整覆盖 PowerShell 的 function、alias 和脚本解析，也不能证明桌面入口的精确版本。

入口发现、后台服务刷新、后台服务包版本必须分别诊断；不要把 update 子命令缺失误判为模型目录无效。删除 function 不保证机器上只剩一个 Codex 安装。

## 2. 当前实现的缺口

后续实现开始时应重新核对以下入口；本设计基于当前未提交的工作区，不要求撤销已有模型目录修改。

- `src-tauri/src/consumer.rs`：`ConsumerRole` 只区分 Desktop、Cli；可信 CLI 路径规则没有单独覆盖 `.codex/packages/app-server-daemon/`。共享后台服务可能落入身份不确定分支，不能被准确展示或协调。
- `src-tauri/src/environment.rs`：供应商应用、OpenAI 登录切换、恢复配置已有 `PendingRestartContext`、操作持久化与消费者身份协调，但未将共享后台服务作为独立对象。
- 同文件的 `repair_model_catalog_inner`：只更新目录的兼容修复路径有备份、校验与回滚，但没有与完整环境切换等价的待刷新协调。该路径必须纳入设计，不能只改供应商应用入口。
- `src/messages.ts`：现有提示要求重启桌面版或 CLI，未说明 CLI 退出后共享后台服务仍可能驻留。
- `src-tauri/src/desktop.rs`：现有桌面控制器只负责可信桌面进程树。共享后台服务应通过独立边界处理，不进入桌面结束集合。
- [ADR-0033](../adr/0033-owned-app-server-process.md)：GPTEasy 会话服务进程由应用独占管理，与用户 CLI 的共享后台服务不同，不能合并生命周期。

## 3. 目标与范围

完整目标是在 Windows、WSL2 与独立 Linux 中提供“选择当前供应商模型 → 选择通用思考强度 → 刷新读取旧配置的运行实例”的可验收路径。Windows 受控 daemon 重启可以作为首个实施阶段：识别共享后台服务 → 配置变更后标记待刷新 → 用户主动确认重启 → 核验并协调状态。WSL/Linux 必须同时解决模型目录缺失与运行实例未刷新，不能只补重启提示就认定跨平台需求完成。

必须满足：

1. 用户不需要逐模型配置 profile，即可继续采用 ADR-0053 的通用思考档位兼容默认值。
2. 用户能看出配置已经保存，以及哪些运行中的程序还可能使用旧配置。
3. 重新打开 PowerShell 不再被提示为共享后台服务刷新完成的充分条件。
4. 用户可以在 GPTEasy 中主动执行一次受控后台服务重启；配置保存本身不执行该操作。
5. 后台服务刷新失败不撤销已成功提交的配置，也不伪装成供应商验证或配置写入失败。
6. 身份、协议或运行状态不能确认时保留待处理状态，提供重新检查和人工操作说明。
7. WSL2 桌面切换、WSL2 内 Linux 脚本切换，以及独立 Linux 的 Bash/Zsh 切换均生成当前供应商的完整模型目录。用户能在 Codex 的 /model 选择已发现模型，并选择 low、medium、high、xhigh；无需逐模型 profile。
8. 配置与目录提交、运行实例刷新、真实菜单验收分别记录结果；缺少 daemon 管理接口不阻断受支持版本的模型目录交付。

Windows 受控重启阶段不包含：后台服务自动升级、自动判断空闲并重启、强制结束用户 CLI、修改 PowerShell function、固定添加 --no-daemon、逐模型 profile、WSL2 或独立 Linux 后台服务控制。也不增加请求代理、额外供应商探测或思考强度转换。

## 4. 生命周期对象

| 对象 | 识别依据 | 配置变更后的处理 | 控制边界 |
| --- | --- | --- | --- |
| ChatGPT/Codex 桌面版 | 当前可信包路径、进程树、PID 与创建时间 | 沿用现有待重启 | 沿用 ADR-0041 的独立用户确认操作 |
| 交互式 Codex CLI | 当前可信 CLI 身份与进程关系 | 保留待重启，提示在原终端退出后重新运行 | GPTEasy 不启动、关闭、终止或重建用户 CLI |
| Codex 共享后台服务 | 默认环境的 daemon 状态与受管进程身份联合校验 | 单独记录待刷新 | 用户明确确认后调用 daemon 管理命令 |
| GPTEasy 会话服务进程 | 应用自有记录、所有权代次、精确进程身份 | 沿用现有独占生命周期 | 从用户消费者与共享后台服务判断中排除 |
| 其他工具的 App Server | 无法归入以上可信对象 | 保留身份不确定提示 | 不接管、不批量终止 |

禁止只按 codex.exe 名称、app-server 参数或目录前缀认领进程。共享后台服务可以承载用户任务，即使没有 CLI 窗口也不能推断其空闲。

### 4.1 可信检测

后端解析当前用户已安装的可信 CLI 入口，并检查目标版本实际提供的 daemon 管理能力。调用绝对路径，固定参数；不执行用户的 codex、codex-full function，不接受前端提供的可执行路径或 shell 命令。

入口发现必须枚举并区分桌面附带可执行文件、npm 启动脚本和其它可信独立安装，记录实际候选及各自管理能力，不能只使用 PATH 首个 codex 或只按版本字符串判断。为同一操作选择确定的、支持目标命令且面向相同默认 Codex home 的可信入口，预览和执行绑定同一入口及最终程序身份。当前用户终端入口与所选管理入口不同，应展示入口来源与差异；多个候选无法可信解歧时要求用户选择后端发现的候选 ID，前端仍不得提交任意路径。具体解析算法在实现前按各安装方式验证，不永久硬编码用户目录，也不假设所有 codex.cmd 都来自同一个包。

检测须交叉确认：

- 目标环境是默认 Codex home，管理命令使用同一个 home；不控制自定义 CODEX_HOME 或另一个用户的服务。
- 管理接口报告的运行状态、backend、服务路径及 PID，与当前用户可访问的实际进程相符。
- 对当前已观察到的 pid backend，核对 PID、进程创建时间、规范化可执行路径、用户归属，以及有限的 daemon 命令身份。
- socket 或控制目录属于目标环境；路径规范化后再判断，不以未经核验的响应路径执行程序。
- GPTEasy 自有会话服务和桌面 bundled App Server 不进入共享后台服务集合。

第一阶段主动重启只支持实际验证的 pid backend。其它 backend 可以展示版本与状态；未建立等价身份核验契约前，重启降级为人工操作。

`version`、帮助检查等探针只有在对应 CLI 版本上确认无启动、安装、更新副作用后才用于自动检查。没有可信入口、命令不支持、超时、JSON 无法解析或进程身份不一致时，结果为 unknown 或 unsupported，不猜测为 stopped。缺失版本字段只显示版本未知；若身份仍能按已验证契约确认，不必因此阻断重启。

## 5. 状态与持久化

服务运行状态和配置刷新状态分开表示。

| 维度 | 建议状态 | 含义 |
| --- | --- | --- |
| 运行状态 | running / stopped / unknown / unsupported | 当前是否有可信的共享后台服务 |
| 刷新状态 | not_required / pending / restarting / refreshed / failed / indeterminate | 对某次已提交配置变更的后台服务刷新结果 |

`refreshed` 表示生命周期核验通过，不代表已验证真实供应商请求或所有现有会话都采用了新参数。菜单是否正确属于独立能力检查或人工验收结果。

### 5.1 沿用待重启聚合

复用现有持久化待重启上下文，增加共享后台服务对象与变更代次；不要增加一套独立的全局“配置已生效”布尔值。

建议记录：上下文版本、环境标识、本次变更代次或操作 ID、目标配置与目录修订、提交时间、变更时观察到的服务身份、检测不确定标记，以及最后一次刷新结果。身份至少包含 PID、创建时间、规范化路径和受管 backend。目标修订采用已有受管工件一致性机制；上下文不复制凭据、目录正文或完整命令行。

全局 `pendingRestart` 继续供现有界面与契约使用，由以下待处理项聚合：桌面消费者、交互式 CLI、共享后台服务以及无法可靠排除的旧消费者。后台服务刷新成功只消除对应服务项，不清空其他消费者的待重启。

兼容旧上下文：旧版消费者身份仍按旧规则协调；缺失共享后台服务证据时执行只读补充检查，不能直接认定已刷新，也不能因升级文档或应用而改写 Codex 配置。若可信服务创建时间早于已知配置提交时点，保守提示待刷新；时间或提交证据不足时显示无法确认。全新接管且没有变更证据时，不捏造历史待刷新记录。

### 5.2 触发规则

| 操作 | 是否生成新的待刷新代次 |
| --- | --- |
| 应用或重新应用供应商，相关工件实际变化 | 是 |
| 当前供应商保存并应用，相关工件实际变化 | 是 |
| 用户确认的“强制设置”/受控配置重建，配置或目录实际变化 | 是；先提交本地配置，再单独协调共享 daemon 刷新 |
| 切换 OpenAI 登录模式、恢复上次配置，相关工件实际变化 | 是 |
| 用户确认的模型目录兼容修复，目录实际变化 | 是，即使 config.toml 不变 |
| 仅修改供应商显示名称、验证未保存、工件完全不变 | 否；已有待刷新状态继续保留 |
| 用户取消或配置变更已完整回滚 | 否；恢复原待处理上下文 |
| 应用启动、打开页面、刷新检测 | 只读协调，不制造配置变更 |
| 外部或人工配置修改 | 按现有冲突规则处理，不自动认领或覆盖 |

对实际变更，写入前读取可信服务身份，提交前后再检测，捕获写入期间出现的服务。提交时点与创建时间无法可靠比较的服务保守保留待刷新。

### 5.3 原子性与恢复

完整环境切换沿用现有 Saga，在准备、提交、恢复路径中一起持久化待处理上下文。目录修复也必须具有可恢复的变更意图与旧/新目录修订，避免目录已换成新内容、待刷新证据却因崩溃丢失。可以复用现有操作日志或为目录修复增加最小日志，不要求把修复升级为供应商重新验证。

恢复时按照磁盘旧/新修订收敛：目录已提交则恢复待刷新，已回滚则保留原上下文，出现第三种修订则进入冲突或无法确认。具体数据库迁移由实现会话选择；验收必须覆盖目录提交与状态提交之间的崩溃窗口。

### 5.4 “强制设置”与共享 daemon 刷新

“强制设置”沿用 [ADR-0043](../adr/0043-confirmed-controlled-config-rebuild.md) 的用户确认后受控配置重建，以及 [ADR-0048](../adr/0048-force-standalone-linux-provider-switch.md) 的独立 Linux 整体替换边界；它不是绕过安全校验的快捷写入。强制设置必须把 `app-server daemon` 刷新纳入同一项可追踪操作，但不能把 daemon 重启失败伪装成配置写入失败，也不能为了重启而破坏已经验证可用的配置。

强制设置的结果拆成两个独立但有顺序的提交结果：

1. **本地配置提交**：恢复点已创建，候选配置、凭据引用和完整模型目录均已写入、复读并通过一致性校验。
2. **共享 daemon 刷新**：在本地配置提交之后，检测并在用户确认后调用同一环境的可信 `app-server daemon restart`，再核验旧/新实例和目标工件修订。

本地配置提交成功后，daemon 刷新失败、取消、不支持或结果不明确，均不得回滚已复读确认的新配置；应保留新配置、完整目录和 `pending`/`failed`/`indeterminate` 证据，让下一次 Codex 启动能够读取一套完整配置。只有配置尚未完整提交、恢复点不可用、并发修改破坏了提交条件或写后校验失败时，才使用恢复点停止并恢复旧配置；这类失败不得启动 daemon 或执行重启。

强制设置采用以下阶段模型，阶段名是验收接口的建议术语，具体持久化载体可沿用现有未完成操作协议：

```text
prepare_force_apply
  -> backup_created
  -> candidate_written
  -> config_verified
  -> catalog_verified
  -> pending_daemon_refresh
  -> restart_preview
  -> restart_confirmed
  -> restart_executing
  -> restart_verified
  -> completed
```

异常收敛阶段为：

```text
failed_and_restored
completed_with_refresh_pending
indeterminate
```

- `completed`：恢复点仍可追溯，本地配置和目录已提交，且共享 daemon 的新身份已核验，或已可靠确认提交前没有需要刷新的旧运行实例；目标工件修订未被外部修改。
- `completed_with_refresh_pending`：本地配置和目录已提交，但仍有或可能有未刷新的运行实例，用户尚未确认、管理能力不支持，或刷新失败；Codex 后续新启动可读取新配置，现有运行实例仍需单独处理。
- `failed_and_restored`：配置提交前或提交过程中失败，旧配置及其目录引用已恢复并通过复读校验；不能留下悬空的 `model_catalog_json` 或半成品目录指针。
- `indeterminate`：无法判断 restart 是否已经发生、外部修改破坏了修订判断，或旧/新服务身份无法可信区分；不得把它当成 stopped、成功或可安全重试。

强制设置提交后，如果检测到可信运行中的共享 daemon，界面须展示“配置已保存，后台服务仍可能使用旧配置”，再提供独立的重启预览和第二次确认。重启确认只授权本次 daemon 重启，不授权升级、切换 CLI 包、结束用户 CLI 或执行前端提供的命令。daemon 已可靠确认停止时不为了“完成强制设置”而启动它；状态为 `unknown` 时不能走 stopped 分支，也不能盲目重启。管理命令超时后禁止自动重试，必须重新探测实际状态，再按旧实例退出、新实例运行和修订一致性收敛结果。

强制设置期间发生崩溃时，下次启动必须依据恢复点、旧/新配置修订、目录引用和 pending context 收敛，而不能因为 UI 没收到成功响应就盲目回滚或重复重启：

- 目录已提交、配置未提交：保留旧配置和恢复点，未引用的完整目录可暂留，不能写入半成品指针。
- 配置已提交、pending context 尚未完成：以复读得到的新配置为准，补建待刷新证据，不覆盖新配置。
- 配置与状态各自出现第三种修订：进入 `indeterminate`/冲突，要求重新检查或人工恢复。
- daemon 可能已经重启但命令无响应：先核验旧/新身份，禁止因为超时再次执行 restart。

“确保 Codex 正常工作”的最低保证是：当前配置语法有效；provider、默认模型、凭据引用和模型目录指针相互一致；目录完整、可读且不含凭据；失败时系统要么保留旧配置，要么保留经过复读校验的新配置；任何可恢复点都不能指向缺失、半成品或被错误覆盖的目录。供应商服务端是否将请求路由到预期分组不属于本地提交保证；例如 DayWay 返回 `GPT-Pro (distributor)` 应作为服务端路由问题单独诊断，不能由强制设置擅自修改本地分组或凭据。

## 6. 用户流程

供应商管理页的环境状态区域增加“共享后台服务”，分别展示运行状态、待刷新提示及已知的 CLI/服务版本。无需新增独立的模型配置页面。

- 已提交配置且后台服务待刷新：“配置已保存。Codex 共享后台服务仍可能使用旧模型目录，重新打开终端不一定刷新。”
- 操作入口：“重启后台服务”“重新检查”。用户关闭页面或选择稍后处理时保留待刷新。
- 确认内容：“后台服务重启可能中断连接它的 Codex 任务。请先结束需要保留的任务。是否继续重启？”
- 重启已核验：“共享后台服务已重启。”如果仍有旧 CLI，补充“请在原终端退出并重新运行 Codex”。
- 结果不明确：“配置已保存，但无法确认后台服务刷新结果。请重新检查或按说明手工处理。”
- 不支持管理接口：“无法由 GPTEasy 重启当前后台服务。”展示适用条件明确的人工步骤。

确认只授权这次后台服务重启，不授权版本升级。CLI 正在运行或任务状态未知时明确展示影响；第一阶段不把进程数量作为任务空闲判断。

前端提交后端生成的短期预览标识，绑定环境、变更代次、已核验服务身份及可信 CLI 入口身份。前端不能指定 PID 集合、路径、附加参数或替代命令。

强制设置的界面必须把上述两个结果分别呈现：先显示“强制设置已保存”或“强制设置已恢复”，再显示“共享后台服务已刷新”“等待刷新”“刷新失败”或“结果不明确”。当本地配置提交成功而 daemon 重启失败时，不显示“强制设置失败”并诱导用户重新覆盖配置；应提供重新检查、再次确认重启和明确的人工恢复路径。强制设置的首次确认说明会重建配置并创建恢复点，daemon 重启的第二次确认说明可能中断正在运行的 Codex 任务。

## 7. 受控重启与核验

1. 后端生成预览，读取待处理上下文、服务身份、CLI 能力和已知版本。
2. 用户主动点击并确认；后端进入与配置修改协调的操作锁，重新检查预览代次、工件修订及所有身份。
3. 配置已变更、服务已换代或 CLI 入口被替换时拒绝过期预览，返回新状态供用户重新操作。
4. 若服务已自然停止，不重新启动它；将旧实例已退出作为该项协调证据。检测为 unknown 时不能采用此分支。
5. 若服务仍可信运行，调用同一环境的可信 CLI：`app-server daemon restart`。使用固定参数、隐藏窗口、管道输出、有限超时；不修改配置，不追加 reasoning 覆盖，不调用 update。
6. 重新检查管理状态与实际进程，确认旧身份已退出、新身份已运行，路径和用户归属仍符合当前契约，新实例创建在目标工件提交之后。
7. 再核对当前工件修订和变更代次；仅协调本次对应的后台服务项，保留仍存活的旧桌面版或 CLI 项。
8. 返回环境实际状态和本次操作结果，前端据此更新，不用命令退出码替代核验。

持锁期间不得同时提交供应商、模式、恢复或目录修复操作。跨进程外部写入不受锁约束，仍通过执行前后的修订检查识别；发现变化时返回 indeterminate 或 conflict，不宣告旧目标已刷新。

### 7.1 成功证据的强度

最小成功条件是旧实例退出、新实例可信运行、目标工件修订未变。UI 只宣告后台服务已重启；既有会话可能保存了显式模型或 effort，仍需在 Codex 中重新选择。

若目标 CLI 提供已验证、无任务副作用的共享 daemon 只读协议，可以附加检查同一服务的 model/list 与当前目录的档位。协议缺失时不捏造该能力；通过新建独立 stdio App Server 得到正确列表，不能证明共享 daemon 已加载新目录。第一阶段至少要求真实 CLI 菜单人工验收。

### 7.2 失败及不确定结果

| 结果 | 状态处理 | 后续操作 |
| --- | --- | --- |
| 服务身份或预览变化 | 拒绝执行，保持对应待处理项 | 重新检查并确认 |
| 命令失败且旧服务仍运行 | failed，保留待刷新 | 用户检查后手动重试 |
| 旧服务退出、新服务未启动 | failed，展示停止状态和错误 | 不自动重复 restart；提供人工恢复说明 |
| 超时、响应损坏、操作中断 | indeterminate，重新读取实际状态 | 不自动重试可能已经执行的重启 |
| 新服务已运行但工件被外部修改 | indeterminate 或 conflict | 按现有外部配置协调流程处理 |
| 服务已停止且可可靠确认 | 消除该旧实例的待处理项 | 不为完成核验而启动服务 |

不得通过扫描全部 codex.exe、直接结束服务 PID、重建 current 包目录或升级服务来补救失败。管理命令超时后即使回收自有命令进程，也不能推断服务操作已取消；须重新检查实际状态。

## 8. 版本展示与后续扩展

第一阶段展示 CLI 版本、受管程序版本及运行中的 app-server 版本，值缺失时显示未知。0.160.0 与 0.157.1 仅为本次机器快照，不作为固定最低版本或上游最新版本。

版本不一致显示普通说明：“后台服务使用独立安装的版本，重启不会升级。”不能仅凭版本不同判定配置刷新失败。

“与当前 CLI 对齐”留给后续独立任务。届时需单独预览与确认，验证目标包、版本、当前任务影响与更新后状态；不可隐含在重启操作内。前序本机帮助已观察到 `app-server daemon update --from-cli -y`，其中 --from-cli 表示复制并固定当前 CLI 包；实现前重新检查目标版本帮助，不能当作所有版本永久提供的接口。

跨 PC 实测进一步确认：该次 update 本身已经重启后台服务，后续应先核验 installedVersion、runningVersion 与实际新实例，不无条件追加 restart。--from-cli 的固定意味着选中当前 CLI 包，不能描述为升级到上游最新版本；恢复常规生产更新的提示也必须使用已核验、确实支持 update 的同一管理入口，不能回退到可能被桌面入口遮蔽的裸 codex。版本对齐的完整产品流程仍不纳入第一阶段。

## 9. 诊断证据

使用现有问题日志与脱敏规则，记录足以区分阶段的最小证据：

- 阶段：detect、prepare_refresh、commit_artifacts、preview_restart、execute_restart、verify_restart、reconcile_pending。
- 变更来源：provider_apply、active_provider_update、force_apply、openai_login、restore、catalog_repair。
- 服务运行状态、backend、身份是否可信、旧/新 PID 与创建时间；路径按已有诊断规则脱敏。
- 已知 CLI/managed/app-server 版本、管理能力分支、有限错误码、超时及核验结果。
- 入口来源（桌面附带、npm、独立安装）、候选数、所选管理入口与终端默认入口是否一致；路径脱敏，记录实际支持的管理子命令。
- 变更代次的脱敏标识、目录策略 ID、配置或目录是否变化、是否还有其他消费者待重启。
- 能力检查标记：not_checked、matched、mismatched、unsupported；不能把未检查记录成通过。

不记录 API Key、auth.json、配置正文、完整命令行、请求内容、供应商地址或未脱敏模型 ID，不直接导出未经筛选的管理命令 stdout/stderr。新增日志必须补回归测试，覆盖阶段区分和敏感字段排除。

## 10. 实现入口与任务顺序

建议建立一个负责“检查、预览、受控重启”的后端服务，隔离 CLI 解析、命令执行、进程检查与时钟边界，供环境协调及 UI 复用。名称和文件划分可在实现时确定，不向前端暴露通用 shell 执行器。

推荐顺序：

1. 验证目标 CLI 的管理契约：只读检查副作用、支持的 backend、JSON 字段、默认 home 选择、重启语义。
2. 增加独立服务身份与消费者分类测试，保留 GPTEasy 自有服务排除规则。
3. 将 ADR-0043/0048 的强制设置接入同一提交与恢复边界，明确本地配置提交和共享 daemon 刷新是两个独立结果。
4. 扩展待重启上下文与恢复逻辑，覆盖完整环境变更、强制设置及目录修复；兼容旧记录。
5. 增加绑定环境、工件修订、可信入口和服务身份的独立预览/确认/执行命令与核验，确保操作锁、过期预览和窗口隐藏。
6. 更新环境状态契约、状态区域、提示和问题日志；保留旧 pendingRestart 的聚合意义。
7. 执行 Windows 自动回归与真实 CLI 菜单人工测试，形成脱敏证据。
8. 按第 14 节交付 WSL/Linux 模型目录：共享生成器与导出载荷、Linux 不可变目录、共同管理 schema、配置切换与恢复、待刷新提示，以及真实 Linux CLI 模型和思考强度菜单验收。可与 Windows 实现分任务推进，不能作为可选项遗漏。功能实现完成后仍保持未发布。

主要参考入口：`consumer.rs`、`environment.rs`、`state.rs`、`desktop.rs`、`diagnostic_report.rs`、`lib.rs`；前端为 `src/contracts/environment.ts`、`src/messages.ts` 及现有环境状态组件。测试可扩展 `consumer_detection.rs`、`environment_workflow.rs`、`diagnostic_report.rs` 并为新后端服务增加契约测试。跨平台入口包括 `src-tauri/src/wsl.rs`、`src-tauri/src/provider/linux_export.rs`、`src-tauri/src/provider/shell_runtime.sh`、`src-tauri/src/provider/model_catalog.rs`、`src-tauri/src/provider/catalog.rs` 及相应 WSL/Linux 导出与恢复测试。

## 11. 自动化验收矩阵

| 编号 | 场景 | 必须断言 |
| --- | --- | --- |
| A1 | 共享 daemon、桌面子进程、自有会话服务和 CLI 同时存在 | 分类准确，只有目标共享服务进入后台重启边界 |
| A2 | 路径相似但 PID、创建时间、用户或命令身份不符 | 不认领、不执行；状态不能误报停止 |
| A3 | 管理命令缺失、不支持、超时、损坏 JSON、未知 backend | 明确降级且无启动/安装副作用 |
| A4 | 应用供应商后旧 daemon 驻留 | 记录目标代次，重新打开 CLI 不消除服务待刷新 |
| A5 | 只更新目录，config.toml 不变 | 同样生成可恢复的待刷新证据 |
| A6 | 写入失败、取消、完整回滚、完全无变化 | 不创建错误的新代次；原待处理状态保留 |
| A7 | 配置与上下文提交之间崩溃、目录修复中断 | 依据旧/新修订恢复；第三种修订进入冲突 |
| A8 | 重启后台服务成功，但旧 CLI 或桌面版仍运行 | 只清除服务项，全局待重启仍为 true |
| A9 | 预览后服务换代、PID 复用、CLI 替换或再次切换配置 | 过期预览拒绝执行 |
| A10 | 命令报告成功但旧服务未退出或新进程不可信 | 不报告成功；保持失败或不确定结果 |
| A11 | 命令超时但操作可能已发生，GPTEasy 重启后恢复 | 无自动重复重启；重新核验真实状态 |
| A12 | 服务自然停止或用户在终端手工重启 | 只读协调收敛，无自动启动或自动重启 |
| A13 | 后台刷新过程中外部修改工件 | 不把旧代次标为当前已刷新 |
| A14 | CLI/服务版本不同或字段缺失 | 不自动更新，不仅凭差异判断故障 |
| A15 | Windows 执行管理命令及脚本入口 | 无可见控制台，参数固定，输出受限 |
| A16 | UI 状态、确认与诊断日志 | 保存与刷新结果分开；敏感值不进入日志 |
| A17 | 桌面 codex.exe 在 PATH 中先于支持管理命令的 npm 入口 | 不错误依赖首个 codex；能力检查区分入口，选择绑定到可信候选并展示差异 |
| A18 | 删除 function，但 alias、脚本或多个独立安装仍可能存在 | 不将 where.exe 结果当作完整 PowerShell 解析；同一次预览、执行和核验使用同一确定入口 |
| A19 | 强制设置前备份失败、候选配置/目录写入失败或写后复读不一致 | 不启动 daemon；使用恢复点恢复旧配置，不能留下悬空目录指针或半成品提交 |
| A20 | 强制设置配置已提交但 daemon 尚未刷新、用户取消确认或管理接口不支持 | 保留可读的新配置和完整目录，进入 `completed_with_refresh_pending`，不把本地成功误报为运行实例已刷新 |
| A21 | daemon restart 失败且旧实例仍在、旧实例退出但新实例未启动 | 保留新配置和待刷新证据；不自动杀进程、不自动重复 restart，给出人工恢复说明 |
| A22 | restart 超时、响应损坏、GPTEasy 在执行中崩溃或重启后再次启动 | 重新探测真实状态；可能已执行时不重试，按旧/新身份和修订收敛为 `completed`、`failed` 或 `indeterminate` |
| A23 | 强制设置期间用户再次切换供应商、外部修改配置或目录 | 修订检查拒绝过期提交或进入冲突；不覆盖外部新状态，不清除新的待刷新代次 |
| A24 | 强制设置成功但服务端仍返回错误分组，或旧 Codex 会话仍保留模型/effort | 不回滚本地配置、不宣告模型菜单已验收；分别记录服务端路由和旧会话诊断 |

核心集成测试必须模拟“活服务保存旧目录 → 写入新目录 → 同一服务仍返回旧档位 → 重启后新服务读取新目录”的真实边界。只断言调用过 restart 或生成了非空 JSON，不能覆盖本次缺陷。

## 12. 本机人工验收

安排没有重要任务的测试窗口，先记录 CLI/服务版本、服务身份与菜单；保全用户配置，测试结束后按既有恢复流程还原。采用真实默认共享 daemon，避免 --no-daemon 绕过待测路径。

1. 启动服务并加载旧目录；通过 GPTEasy 明确应用新的通用四档目录，或在可适用的隔离场景执行目录兼容修复。
2. 确认 UI 显示配置已保存、后台服务待刷新；另开 PowerShell，检查提示没有把它认作刷新完成。
3. 在 GPTEasy 中主动重启后台服务，确认新身份运行且没有服务自动升级。
4. 用纯 codex.cmd 进入 /model 并选择模型，确认能进入 Low / Medium / High / Extra high。
5. 用原有 codex-full function 重复菜单检查；另测 codex-full --no-daemon 作为对照，保留 function 原始定义。
6. 检查旧 CLI 存活时其待重启项仍保留；用户退出重开后状态协调收敛。
7. 检查失败分支提示和问题日志：目录已经保存但刷新失败时，未误报保存失败、未泄露凭据、未自动重复操作。
8. 在配置损坏或冲突场景执行强制设置，分别验证“重建成功但 daemon 待刷新”和“提交前失败并恢复旧配置”；模拟 restart 超时后确认不会自动重复重启。

成功标准是共享服务生命周期、持久化状态和真实菜单三者都有对应证据。菜单有四档不等于四档请求已通过真实供应商，也不等于已有会话的显式 effort 已被覆盖。自动测试不能代替此项人工结果，未执行不得记为通过。

## 13. 实现前须验证的接口事项

- 各目标 CLI 上哪些 daemon 命令确实只读，以及参数和输出的稳定性。
- 桌面附带入口、npm 脚本及最终二进制的解析关系；PATH、PowerShell、NVM 路径变化时如何保持入口身份一致。
- 是否能对同一共享服务执行无副作用的 model/list；没有则保留人工菜单验收。
- 重启期间仍连接的 CLI 的行为，以及新服务启动完成的可观测条件。
- 配置提交时间与服务创建时间精度、旧上下文迁移和目录修复日志的最小恢复方案。

这些事项是实现会话的首批验证任务；验证失败时按本文降级，不扩大到任意进程控制、自动更新或批量杀进程。


## 14. WSL2 与独立 Linux 的模型选择与运行实例刷新

本节将 WSL2/Linux 模型选择和通用思考强度选择明确列为完整交付的必做范围，并规定相应运行实例刷新边界。主动 guest/shell 后台服务管理仍是独立后续扩展，不加入 Windows 受控重启阶段。本提案尚未改变已生效的 [ADR-0030](../adr/0030-shared-wsl-management.md) 与 [ADR-0031](../adr/0031-safe-wsl-lifecycle-restoration.md)。Windows 的实测不能证明 Linux CLI 提供相同 daemon 子命令、backend 或生命周期语义；实现前须在目标 Linux 安装上另行验证。

### 14.1 环境隔离与管理入口

刷新目标以运行环境、用户身份和目标 Codex home 联合确定，不能把一台 PC 建模为只有一个共享后台服务。

| 环境 | 目标边界 | 管理入口要求 |
| --- | --- | --- |
| 原生 Windows | 当前 Windows 用户的默认 Codex home | 第一阶段已核验的 Windows CLI 入口 |
| WSL2 | 发行版注册 GUID、默认 Linux 用户及其默认 Codex home | 在该发行版中核验的原生 Linux CLI；桌面当前不扩展自定义 home |
| 独立 Linux 脚本 | 当前 Linux 用户 UID 与本次实际写入的 CODEX_HOME，未设置时为 $HOME/.codex | 同用户、同目标 home 的原生 Linux CLI |

Windows 服务刷新不能清除 WSL 的待处理状态；一个发行版的刷新不能清除另一发行版的状态。脚本若在 WSL 内指定自定义 CODEX_HOME，该目标不能与桌面管理的默认 home 合并。不同用户、sudo/root 环境同样隔离，不能通过提升权限重启其他用户的服务。

命令入口必须核验实际安装、最终程序及管理能力。WSL 中不能因 PATH 命中 `/mnt/c/...` 下的 Windows codex.exe 或 codex.cmd，就将它作为 guest 服务管理入口；遇到互操作入口时说明环境不匹配，要求选择或安装合适的 Linux CLI。Bash/Zsh 的 alias、function、npm 包和多个安装也可能改变解析结果；当前脚本的 command -v 与 WSL 的 type -P 都不足以独自证明目标管理能力。配置写入最低兼容版本检查与 daemon 管理能力检查分开，不能仅凭版本通过就运行 restart。

Linux 的只读检查命令、backend、socket 归属、PID 身份及重启结果须建立独立契约，不直接套用 Windows pid backend 的路径规则；也不假定必有 systemd 或某个固定服务单元。没有经核验的接口时提示人工处理，不自动调用安装、update、start 或通用进程终止命令。

### 14.2 WSL2 生命周期与待刷新状态

沿用发行版内共享配置锁和桌面 SQLite Saga，shell 不复制桌面的持久化状态机。配置变更与运行实例刷新分开表达；第一阶段的 Windows 重启按钮不路由到 WSL。

- Running 发行版：配置提交或显式刷新观察到脚本变更后，沿用保守待重启状态，提示在该发行版内处理可能驻留的共享服务。退出 WSL 终端窗口不能作为服务已退出的证据。尚无可信 guest 服务检测时，不能将提示写成“已检测到后台服务”。
- Stopped 发行版：普通检查不进入 guest、不启动发行版、不运行 Codex 探针，只显示最后观察状态及待核验说明。用户明确执行刷新实际状态、核验或切换时，才沿用当前契约临时启动。
- 发行版已实际停止：可以按 ADR-0030 协调该发行版旧运行实例的待处理状态；不为验证后台服务而另行启动。此协调不等于已验证下一次启动的模型菜单，也不能清除其它环境的状态。
- 临时启动后的收尾：退出桌面自有 guest 进程、释放配置锁，最多观察自然停止 10 秒。后台服务或其他负载使发行版仍 Running 时保留实际状态并说明，绝不调用 wsl --terminate，也不为恢复 Stopped 而结束 daemon。

未来若提供“重启此发行版后台服务”，必须另行明确扩展 ADR-0030 的控制边界，并验证 guest 内服务身份、默认用户/home、入口、用户确认及结果协调。重启操作与配置写入共用发行版内协调锁，预览绑定目标工件修订，避免桌面与 shell 并发切换；结果只协调对应后台服务项，不能推断其它旧 CLI 已刷新。不得把重启整个发行版作为后台服务 restart 的替代方案。

### 14.3 Linux 切换与恢复后的刷新提示

当前脚本切换后输出“已切换到”，恢复后输出“已恢复最近一次 shell 切换前的配置”，但没有统一说明共享后台服务可能仍保留旧配置。旧凭据清理警告中的“新配置已经生效”也容易混淆磁盘提交与运行实例刷新。后续文案任务应统一成功切换与成功恢复后的说明，例如：

> 配置已保存。正在运行的 Codex CLI 或共享后台服务可能仍使用旧配置。请先结束需要保留的任务，再在当前用户及本次目标 Codex home 下刷新运行实例；重新打开终端不一定刷新共享后台服务。

提示是保守说明，不声称已检测服务、不自动执行任何生命周期命令。仅在本次目标 Linux CLI 的帮助及管理契约已核验后，才可展示适用的人工命令：`<已核验 Linux CLI 绝对路径> app-server daemon restart`。必须同时说明目标 home；自定义 CODEX_HOME 需要与切换时一致。不能无条件推荐裸 codex、Windows codex.cmd 或 sudo，也不附带 update --from-cli。不支持 daemon 管理时说明限制，让用户按该安装的受支持方式自行刷新；不把缺失管理能力升级为配置写入失败。

source 导出脚本仍只定义函数与常量，不能执行 Codex 版本/帮助/服务探针、访问网络、写配置或启动服务。切换与恢复继续使用现有 Bash/Zsh 协议、备份和共享锁，不引入 Python、Node、jq 或 Windows SQLite 依赖。codex-full 继续表达用户的启动偏好，不固定追加 --no-daemon，也不在每次启动时重启服务。

如后续需要脚本中的主动 daemon 管理入口，应作为独立用户操作单独设计：明确任务中断影响，绑定当前 UID、目标 home、可信 Linux CLI 与配置修订；按已验证契约检查并核验结果，操作不明确时不自动重复。该功能需要另行修订“shell 不检测或控制 Codex 进程”的既有决策，不能作为本节文案改进的隐含实现。后台刷新失败不撤销成功配置提交。

### 14.4 必做：WSL/Linux 模型目录与选择器支持

当前 [ADR-0053](../adr/0053-common-reasoning-selector-defaults.md) 只为原生 Windows 生成通用四档目录，这是实现现状，不是本需求对 Linux 的范围限制。本提案将 [ADR-0049](../adr/0049-provider-model-catalog-and-reasoning-capabilities.md) 的当前供应商模型目录和 ADR-0053 的兼容默认值扩展到 WSL2 与独立 Linux；在本提案接受与实现前，不宣称这些能力已存在。

#### 14.4.1 用户行为与目录规则

用户通过桌面为 WSL2 选择供应商，或在 WSL2/独立 Linux 中通过 Bash/Zsh 脚本选择供应商后，新启动或已正确刷新的 Linux Codex 必须能够：

1. 在 /model 中列出当前供应商已验证快照中的全部发现模型，默认模型必须存在，不能只导出默认模型一项。
2. 选择其中任一模型后，显示 low、medium、high、xhigh，目录默认 high。OpenAI、DeepSeek、兼容供应商与未知模型采用同一通用规则，无需逐模型 profile 或手工增补能力字段。
3. 请求继续路由到当前供应商；切换供应商时替换活动目录，不合并不同供应商模型，即使两者存在同名模型也不能串用路由。

各平台复用 `model_catalog.rs` 的完整 JSON schema、去重与默认模型补入规则、`common-reasoning-selector-v1` 策略及未知能力描述。supported_reasoning_levels 不省略、不生成空列表；default_reasoning_level 为 high，不能用 null 作为通用默认。图片等其它兼容字段沿用共享模板，不新建一份 Linux 能力规则。具体 schema 必须在目标 Linux CLI 上验证，不能将 Windows 解析通过当作 Linux 已验收。

根级 model_reasoning_effort 仍遵循 ADR-0051 的供应商映射，与目录档位分开：已确认的 OpenAI/DeepSeek 映射保持 high，未映射供应商省略字段，由 Codex 使用目录默认值。下一次明确切换或重新应用生成新的受管配置时清理旧根级 none，不在 source、启动或只读刷新时修改配置。已有会话显式模型与 effort 仍由用户在 Codex 中重新选择。目录开放四档不代表模型已通过四档真实请求验证。

#### 14.4.2 模型数据与离线导出

桌面 WSL 写入从已保存供应商的有效模型目录快照生成；Linux 导出则在导出时携带每个已验证供应商对应的完整目录载荷。两者均核验快照与供应商验证组合的绑定关系，不把 Codex 内置目录当作供应商发现列表，也不额外请求 /models。

Linux 导出建议由 Rust 共享生成器预先序列化每个供应商的 JSON，并以不执行内容的函数/引用式 here-document 携带，同时保存生成协议版本、供应商 ID、对应默认模型和模型 ID 集合等可校验信息。shell 在用户显式切换时取出对应载荷并写文件，不在目标机从任意模型名推断能力，不新增 Python、Node、jq 依赖。JSON、shell 字符串和 here-document 边界必须分别安全序列化；模型 ID、描述、服务地址等输入不得成为代码或路径。source 只建立定义，不写目录、不探测 Codex、不访问网络。

导出载荷携带由共享生成器计算的字节摘要；明确切换时使用现有 SHA-256 工具核验候选文件，并核对供应商与默认模型的绑定元数据。这是导出数据的完整性校验，摘要不作为已应用证据写入目标环境，也不作为供应商验证成功的替代证明。shell 不用正则重建任意 JSON；不能核验的载荷不得提交。

模型快照缺失、验证绑定失效、载荷损坏或生成失败时，在导出/切换的提交前报出可处理原因，要求重新验证或重新导出，保留既有可用配置；不得默默只输出默认模型或成功生成无目录配置。用户不需要为这种恢复逐模型编写 profile。

导出仍是离线快照，供应商重新验证后须重新导出才能在 Linux 脚本中取得新模型。保留已有供应商表的可维护性，同时明确目录载荷的约束：改动默认模型、模型集合或供应商关键组合时，必须同步重新生成对应载荷及绑定元数据；陈旧载荷在明确切换时拒绝使用，不通过 eval 或临时网络请求自动补全。单纯显示名称变更不改变模型集合。导出载荷校验不等于目标环境的已应用证据，不增加 shell 的跨操作哈希状态机。

#### 14.4.3 Linux 路径与不可变目录

目录必须写入本次实际目标 Linux Codex home，建议布局为 `${CODEX_HOME:-$HOME/.codex}/.gpteasy-shell/model-catalogs/<source-id>/<opaque-id>.json`。目录名和文件名由受控 ID 生成，不使用供应商名称、模型 ID 或地址作为路径。每份已提交目录不可变，新版本写新文件，不覆盖旧文件。

配置的根级 model_catalog_json 只出现一次，指向已完成写入的 Linux 目录绝对路径，使用正确的 TOML 字符串转义。路径在目标 Linux 环境内解析，不使用 Windows 盘符、宿主路径或依赖当前工作目录；自定义 CODEX_HOME、空格及非 ASCII 路径均需覆盖。config.toml 为受支持的 symlink 时，模型目录仍位于明确选择的 Codex home，不随配置链接目标悄悄改到其它环境。

延续现有私有目录、文件身份和所有权校验，受管目录不接受 symlink/hardlink 替代，也不读取响应给出的任意路径。目录载荷不得包含 API Key。外部目录只按原配置指针保留，不接管、不删除、不覆写。

#### 14.4.4 配置提交、恢复与清理

使用“先提交不可变目录，再原子切换配置引用”的方案，避免脚本同时替换一个共享目录文件和 config.toml 后产生不同步状态。一次明确切换在现有共享锁内完成：

1. 检查目标环境身份、CLI 的目录兼容性、供应商快照绑定及完整载荷；取得旧配置和本次恢复点，保留旧配置引用的受管目录。
2. 在目标私有目录写候选，核验字节及受控文件身份，按现有持久化要求同步后提交为唯一的新目录文件。最终目录未就绪时，绝不写入指针。
3. 生成包含路由、默认模型、根级 effort 与新 model_catalog_json 的完整配置候选；复核并发修改、锁和 config symlink 身份后，原子替换配置并复读确认。配置替换是活动模型目录切换的提交点。
4. 桌面 WSL 将目录引用、目标修订和待刷新纳入既有 Windows SQLite Saga；shell 继续只在当前操作内核验并提供完整恢复点，不复制 SQLite，也不引入 ADR-0029 排除的跨操作哈希/未完成操作记录。
5. 配置提交失败时保留旧指针与旧目录；目录已就绪但配置未提交而崩溃时，最多留下未引用文件，不能出现指向半成品目录的配置。配置提交后进程中断，磁盘新配置仍指向完整目录，不能仅因未打印成功提示就将其判为未提交或盲目覆盖。

restore 恢复旧配置及原存在性时，必须确保它引用的受管目录仍可用；不可变文件仍在时只需恢复指针，不必重新生成旧目录。若有效恢复点所需目录意外缺失，停止恢复并明确说明，不写入悬空指针。恢复到原来没有目录引用的配置时不强行补目录；恢复到没有 config.toml 的状态也应正确处理。恢复仍需提示运行实例可能未刷新。

目录清理与凭据清理一样，须在共享锁内扫描当前配置、双方恢复点/桌面备份和有效操作的引用；引用不确定时保留，不按文件年龄直接删除。首个跨平台实现可以暂不自动清理目录，优先保证所有有效恢复点可用。不得以删除旧目录促使驻留服务刷新。

#### 14.4.5 WSL 桌面与脚本共同管理协议

双方共同升级管理区块协议，建议引入 schema v2，表达模型目录相对受管路径、生成策略/协议版本与供 Codex 使用的根级绝对路径；两个路径必须指向同一目标工件。桌面与 Bash/Zsh 都要能识别、写入、恢复对方创建的有效目录引用，不能出现只有桌面理解目录而脚本切换时丢失字段的中间交付。

现有 schema v1/旧格式在只读检查时保留并提示缺少目录能力，不自动迁移。用户下一次明确切换或重新应用时，在备份和共享锁保护下生成新目录并写入新格式。新版本仍识别有效旧格式；旧导出脚本遇到未知新 schema，状态读取沿既有规则报冲突，不误报当前目录有效。ADR-0048 所授权的独立脚本整体替换路径可能将新配置恢复为旧格式，应在文档和验收中说明需重新导出；不能修改旧文件后声称旧脚本已具备四档支持。

桌面只读协调应分开报告供应商关键组合有更新、目录缺失/损坏、目录策略旧版及运行实例待刷新。来源 ID 和物理目录路径不同不等于供应商发生变化。不同导出时点的模型集合差异应标明为目录快照差异；由用户明确重新应用更新，不在状态读取时把较旧脚本的目录替换成桌面新快照，也不根据目录差异恢复已删除供应商。

最小受控日志补充生成来源、目录策略/协议版本、模型数量、是否包含默认模型、配置指针是否有效、提交或恢复阶段及待刷新结果。目录正文、完整模型 ID、凭据和服务地址不进入日志；新增日志补阶段区分与敏感字段排除回归测试。

#### 14.4.6 运行实例刷新与兼容失败

目录提交后，WSL 桌面保守记录待重启，脚本按第 14.3 节统一提示。缺少可信 daemon 管理接口时仍可交付目录及人工刷新流程，不要求为支持菜单先升级 daemon 或实现 shell 主动进程控制。若目标 CLI 本身不支持目录配置或完整 schema，则在写入前停止并说明版本/契约不兼容，不静默去掉 model_catalog_json；升级仍由用户单独决定。

支持共享 daemon 的环境按第 14.1/14.2 节确定目标并人工或未来受控重启；没有共享 daemon 的安装由用户退出旧 CLI 后重新启动。可在已核验支持该参数时用 --no-daemon 作诊断对照，不固化到 codex-full。运行实例刷新失败不撤销已成功提交的目录与配置；daemon 已重启也不能直接宣告模型选择已验收。

#### 14.4.7 完成交付的证据

必须分别提供 WSL2 桌面切换、WSL2 内 Bash/Zsh 脚本切换及独立 Linux Bash/Zsh 的证据：目录/schema 可读、真实 CLI 能列出多个当前供应商模型、选中非默认模型后出现四档、切换供应商与 restore 后目录和路由一致。包含 OpenAI、DeepSeek 及未知模型的兼容条目，但不把四档菜单通过记为真实供应商四档请求验证。

有共享 daemon 的测试必须额外覆盖“旧实例读取旧目录 → 新配置与目录提交 → 刷新后真实菜单读取新目录”；无 daemon 环境覆盖旧 CLI 退出后新 CLI 加载。隔离 stdio App Server 的解析结果只作为 schema 证据，不能替代同一共享 daemon 的刷新证据。Linux 接口与菜单均未实测时保持未验收，不能以 Windows 测试通过或文案完善代替本节完成条件。

建议按以下顺序安排实现任务：

1. 验证目标 Linux CLI 的目录配置/schema 契约；扩展共享生成器调用与导出载荷，覆盖完整模型快照和通用四档。
2. 同步实现 WSL 桌面与 Bash/Zsh 的新管理协议、不可变目录、配置引用、恢复和引用保留；补齐切换/恢复提示，验证 source 无副作用。
3. 在 WSL2 与独立 Linux 上验收真实模型和思考强度菜单，并覆盖已有 daemon 的人工刷新路径及无 daemon 路径。完成前两步而未验证真实菜单不能认定跨平台需求完成。
4. 如需产品内主动 guest/shell 刷新，再独立验证 Linux daemon 管理契约并扩展控制决策；版本更新始终为独立操作。

Windows 阶段可先完成，但完整需求不得以“Linux 后续可选”结案。模型目录生成、配置提交、运行实例刷新和菜单验收可以分任务推进，最终必须一起满足跨平台完成条件。
