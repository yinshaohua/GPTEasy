# 供应商保存流程修复方案

- 方案日期：2026-09-26
- 适用范围：供应商详情页，重点是“DayWay企业级稳定”重新验证和保存流程
- 实施状态：已实施并补充回归测试；未发布
- 目标实施文件：`src/ProviderPage.tsx`、`src/messages.ts`、`src/App.test.tsx`

## 1. 背景与问题

本方案已按下文目标实施。本文保留问题背景、决策依据和验收记录，后续实现以当前代码、测试和 `docs/ui/PROVIDER-MANAGEMENT-SPEC.md` 为准。

本机测试“DayWay企业级稳定”时，获取模型后点击“重新验证”可以成功，但验证完成后“保存”按钮仍为灰色，无法继续保存。

同时，当前保存流程存在另一条不可继续的路径：

1. 新建供应商，或修改已保存供应商的关键配置。
2. 页面尚未获取模型，模型列表为空。
3. 用户点击“保存”。
4. 页面直接显示“需要验证供应商”弹窗。
5. 弹窗中的“开始验证”按钮又因为没有模型或没有默认模型而不可用，用户无法继续。

期望行为如下：

- 只要名称已填写且当前没有执行操作，“保存”按钮始终可以点击；不能因为没有字段变更或尚未验证而将保存按钮置灰。
- 保存时根据当前状态引导用户补齐前置条件，而不是让用户进入不可继续的验证弹窗。
- 尚未获取模型时，提示用户获取模型；用户确认后直接执行现有“获取模型”流程。
- 获取模型成功后只展示模型列表，由用户选择默认模型，不自动保存、不自动验证、不自动选择模型。
- 已有模型但尚未选择默认模型时，提示用户选择模型，不调用验证接口。
- 已选择默认模型但尚未验证时，复用现有验证弹窗和验证后自动保存能力。
- 未验证的关键配置不得绕过验证直接保存。

## 2. 已确认的现状与根因

### 2.1 保存按钮被 `dirty` 错误限制

`src/ProviderPage.tsx` 当前保存按钮条件等价于：

```ts
const canSave = name.trim().length > 0 && !busy && (selected ? dirty : true);
```

已保存供应商重新验证成功后，如果名称、服务地址、API Key 和默认模型均未产生待保存变更，`dirty` 为 `false`，因此保存按钮被禁用。验证是否成功不应决定保存按钮是否可点击。

建议将可点击条件收敛为：

```ts
const canSave = name.trim().length > 0 && !busy;
```

该调整只解决按钮可点击性；是否允许实际保存仍由 `saveProvider()` 根据供应商状态、关键配置变更和验证回执进行判断。

### 2.2 `saveProvider()` 没有区分模型准备阶段

当前保存入口的前置判断为：

```ts
if ((!selected || criticalDirty) && !validatedReceipt) {
  setConfirmation("validation");
  return;
}
```

这会把以下三种不同状态全部归入“需要验证”：

- 完全没有模型列表；
- 有模型列表但没有默认模型；
- 已有默认模型，但尚未产生有效验证回执。

而“开始验证”本身受以下条件限制：

```ts
const canValidate = models.length > 0 && defaultModel.length > 0 && !busy;
```

因此第一种和第二种状态会进入验证弹窗，但无法开始验证。

### 2.3 可复用的现有能力

本次方案不要求新增后端命令，优先复用当前实现：

- `discoverModels()`：清除旧验证回执、清空模型和默认模型，并按新建或更新场景调用模型发现命令。
- `runValidation(true)`：执行完整验证，并标记验证成功后继续保存。
- `closeValidationSession()`：验证成功且需要继续保存时调用 `saveProvider(receipt)`。
- `acceptAddressSuggestion()`：接受服务地址建议后，能够沿用验证回执继续保存。
- 现有 `saveDaywayProvider`、`saveVerifiedProvider`、`saveProviderUpdate` 和重命名流程。

## 3. 目标状态分流

保存按钮点击后按以下顺序处理。顺序很重要：先处理模型准备，再处理验证，避免打开不可继续的验证弹窗。

### 3.1 通用前置条件

1. `name.trim().length === 0` 时保存按钮继续保持禁用，避免产生无名称供应商。
2. `busy === true` 时保存按钮继续保持禁用，避免并发发现、验证、保存或删除请求。
3. 除以上两种情况外，保存按钮保持可点击，包括已保存供应商无字段变更的情况。

### 3.2 新建供应商或关键配置已变更

对新建供应商（`selected === null`）或已保存供应商关键配置已变更（`criticalDirty === true`）的保存请求，按以下状态分流：

| 当前状态 | 保存点击后的行为 | 不应发生的行为 |
| --- | --- | --- |
| `models.length === 0` | 打开“需要获取模型”确认框 | 不直接打开验证框，不调用验证接口 |
| 有模型但 `defaultModel.length === 0` | 打开“请选择默认模型”提示框 | 不调用验证接口，不保存 |
| 有模型、有默认模型、没有有效验证回执 | 打开现有“需要验证供应商”确认框 | 不绕过验证保存 |
| 有模型、有默认模型、有有效验证回执 | 沿用现有保存逻辑 | 不重复强制验证 |

### 3.3 已保存供应商且关键配置未变更

当 `selected !== null && criticalDirty === false` 时，继续沿用现有重命名语义：

- 保存按钮可点击，即使 `dirty === false`。
- 不因为保存按钮放开而强制获取模型或重新验证。
- `saveProvider()` 继续调用 `renameProvider(selected.id, name)`。
- 用户刚完成重新验证后点击保存，不应再被按钮禁用阻断。

这样可以避免把“只修改名称”或“重新验证后的无关键配置变更”误判为需要完整验证的更新。

## 4. 确认框与交互设计

### 4.1 扩展确认状态

当前类型为：

```ts
type Confirmation = "discard" | "validation" | null;
```

建议至少扩展为：

```ts
type Confirmation =
  | "discard"
  | "validation"
  | "model_discovery"
  | "model_selection"
  | null;
```

不建议用一个“验证”弹窗承载模型发现、模型选择和完整验证三个阶段，因为每个阶段的前置条件和主操作不同。

### 4.2 “需要获取模型”确认框

建议文案：

- 标题：`需要获取模型`
- 内容：`当前还没有模型列表，请先获取模型。获取成功后请选择默认模型。`
- 主按钮：`获取模型`
- 次按钮：`继续编辑`

主按钮行为：

1. 关闭确认框：`setConfirmation(null)`。
2. 调用现有 `discoverModels()`。
3. 成功后停留在详情页，展示模型列表。
4. 保持 `defaultModel` 为空，等待用户主动选择。
5. 不自动调用验证，不自动保存。

失败时沿用现有模型发现错误展示和脱敏技术详情，不改变确认框语义。

### 4.3 “请选择默认模型”提示框

建议文案：

- 标题：`请选择默认模型`
- 内容：`已获取模型，但尚未选择默认模型，请从列表中选择后再保存。`
- 主按钮：`去选择模型` 或 `继续编辑`

主按钮和次按钮都不应调用验证接口。关闭后用户可以在详情页的默认模型选择框中完成选择；如果现有组件支持聚焦，应将焦点移到默认模型选择控件，提升键盘操作可达性。

### 4.4 “需要验证供应商”确认框

保留当前验证弹窗及其费用提示：

- 只有 `models.length > 0 && defaultModel.length > 0 && !validatedReceipt` 时才进入该弹窗。
- “开始验证”继续调用 `runValidation(true)`。
- 验证成功后继续使用 `saveAfterValidation` 和 `closeValidationSession()` 自动保存。
- 验证失败时停留在当前编辑状态，允许用户修正配置后重试。

验证弹窗的主按钮不应再承担“获取模型”或“选择默认模型”的职责。

## 5. 建议的实现步骤

### 5.1 调整保存按钮条件

在 `src/ProviderPage.tsx`：

1. 移除 `canSave` 对已保存供应商 `dirty` 的依赖。
2. 保留名称非空和非忙碌条件。
3. 保留 `dirty` 用于返回确认、字段变更判断和 `criticalDirty` 计算，不要删除该状态。

### 5.2 抽取保存前置分流

在 `saveProvider()` 开始处增加明确的状态判断，建议逻辑顺序如下：

```ts
if ((!selected || criticalDirty) && !validatedReceipt) {
  if (models.length === 0) {
    setConfirmation("model_discovery");
    return;
  }
  if (defaultModel.length === 0) {
    setConfirmation("model_selection");
    return;
  }
  setConfirmation("validation");
  return;
}
```

实现时应根据项目现有类型和回执来源调整变量名，并确保“有效验证回执”判断不被空值、过期回执或地址建议状态误判。

### 5.3 接入两个新确认状态

在详情页现有确认框区域增加：

- `confirmation === "model_discovery"`：确认后关闭弹窗并调用 `discoverModels()`。
- `confirmation === "model_selection"`：关闭提示框并回到编辑状态；不要调用后端命令。

确认框主按钮在非忙碌状态下应可用。模型发现执行期间由页面现有 `busy` 状态和按钮加载态防止重复操作。

### 5.4 增加界面文案

在 `src/messages.ts` 增加与现有 `providerMessages` 风格一致的字段，建议包括：

- `modelDiscoveryRequiredTitle`
- `modelDiscoveryRequiredMessage`
- `startModelDiscovery`
- `modelSelectionRequiredTitle`
- `modelSelectionRequiredMessage`
- `chooseModelToContinue`

如已有通用“继续编辑”文案，应复用而不是重复增加同义字段。文案应明确下一步，但不要承诺模型发现后会自动保存或自动验证。

### 5.5 保留地址建议流程

不要因为保存按钮始终可点击而改变服务地址建议逻辑：

- 获取模型发现到候选地址时，候选地址仍然只是建议，不得静默回填或保存。
- 完整验证返回 `addressSuggestion` 时，继续使用现有“建议修正服务地址”弹窗。
- 用户接受建议地址后，继续使用现有验证回执保存路径。
- 用户拒绝建议地址时，不能使用候选地址的验证结果保存原地址。
- 已保存供应商采用建议地址后，仍要求用户明确点击“保存”或“保存并应用”。

## 6. 日志与脱敏证据

本问题的失败阶段容易被混淆为“验证失败”，因此实施时应同时评估现有问题日志是否能区分以下阶段：

- 保存点击时的供应商类型：新建或已保存；
- `criticalDirty` 状态；
- 模型数量是否为零；
- 是否已选择默认模型；
- 是否存在有效验证回执；
- 保存前实际进入的分流：获取模型、选择模型、验证或直接保存；
- 模型发现、验证、保存的成功或失败阶段。

如现有日志缺少这些信息，可增加最小结构化日志或测试可观察的事件记录。日志要求：

- 不记录 API Key、完整请求/响应正文或完整服务地址中的敏感信息。
- 不记录会导致凭据泄露的验证上下文。
- 供应商标识使用现有安全标识或脱敏标识；不要新增明文凭据日志。
- 仅在分流决策和请求结果处记录必要字段，避免每次渲染产生噪声。

若新增日志字段，必须同步增加对应回归测试，至少验证“无模型进入模型发现分流”和“有模型无默认模型进入模型选择分流”没有被错误记录为验证分流。

## 7. 测试方案

在 `src/App.test.tsx` 增加或调整前端行为测试，优先通过用户可见按钮和文本验证行为，并断言后端命令 mock 的调用情况。

### 7.1 保存按钮可用性

1. 打开已保存供应商详情页，不修改任何字段，断言“保存”按钮可用。
2. 模拟已保存供应商重新验证成功，断言验证完成后“保存”按钮仍可用。
3. 保留名称为空和请求进行中时按钮不可用的断言。

### 7.2 无模型时的保存分流

1. 新建供应商，填写名称、服务地址和 API Key，但不获取模型。
2. 点击“保存”，断言显示“需要获取模型”而不是“需要验证供应商”。
3. 断言此时没有调用验证或保存命令。
4. 点击“获取模型”，新建场景断言调用 `discover_provider_models`。
5. 对已保存供应商关键配置变更场景，断言调用 `discover_provider_models_for_update`。

### 7.3 获取模型后的选择分流

1. 模型发现成功后断言模型列表可见。
2. 断言默认模型没有被自动选中。
3. 断言模型发现成功后没有自动调用验证或保存命令。
4. 模型存在但未选择默认模型时点击“保存”，断言显示“请选择默认模型”。
5. 断言该状态不调用验证接口。

### 7.4 选择模型后的验证和保存

1. 选择默认模型后点击“保存”，断言显示现有“需要验证供应商”弹窗。
2. 点击“开始验证”，断言调用正确的新建或更新验证命令。
3. 模拟验证成功，断言沿用现有自动保存链路。
4. 断言未验证配置不能直接调用保存命令。

### 7.5 地址建议回归

1. 覆盖验证返回建议服务地址的场景。
2. 断言用户未接受建议前不会静默修改或保存地址。
3. 断言接受建议后仍按现有流程继续保存。
4. 断言拒绝建议后不会使用候选地址的验证结果保存原地址。

## 8. 验收标准

- “DayWay企业级稳定”重新验证成功后，保存按钮不再因 `dirty === false` 变灰。
- 已保存供应商无字段变更时，保存按钮可点击并保持现有重命名语义。
- 新建或关键配置变更且无模型时，点击保存先提示获取模型，用户确认后才调用模型发现。
- 模型发现成功后，列表展示正常，默认模型由用户选择，不自动保存或验证。
- 有模型但无默认模型时，点击保存只提示选择模型，不调用验证接口。
- 有模型且已选择默认模型但未验证时，点击保存进入现有验证确认框。
- 验证成功后继续现有自动保存流程，且未验证配置不能绕过验证保存。
- 地址建议确认、拒绝和后续保存行为与现有规范保持一致。
- 新增或调整的日志不会暴露 API Key、完整请求/响应或其他敏感内容。
- 对应前端回归测试覆盖上述分流，且不破坏现有验证、保存并应用和重命名测试。

## 9. 非目标与实施边界

- 不修改 Rust 后端命令协议、验证算法或模型发现协议。
- 不改变“获取模型”本身的地址探测、建议地址和错误处理策略。
- 不允许通过移除验证判断来保存未验证的关键配置。
- 不把模型发现成功等同于完整供应商验证成功。
- 不在本次修改中处理 Codex 配置文件中 `model_providers.custom.*` 未识别设置的 warning；该 warning 与本保存流程问题分开诊断。
- 本方案完成后仍保持未发布状态，不执行打 tag、发布到 GitHub 或发布到 Gitee。
