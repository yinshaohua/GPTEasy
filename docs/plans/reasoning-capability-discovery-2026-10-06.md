# 推理档位能力发现与兼容兜底设计方案

- 方案日期：2026-10-06
- 文档类型：实现方案与验证记录
- 实施状态：已在 2026-10-07 实施代码修复；未修改用户配置，未发布
- 适用范围：Windows 当前用户 Codex 环境、WSL2、独立 Linux 导出
- 相关证据：[`docs/evidence/windows-reasoning-selector-2026-10-06.md`](../evidence/windows-reasoning-selector-2026-10-06.md)
- 相关决策：[`ADR-0049`](../adr/0049-provider-model-catalog-and-reasoning-capabilities.md)、[`ADR-0051`](../adr/0051-reasoning-effort-and-selector-range.md)

## 1. 背景与问题

GPTEasy 为当前活动供应商生成 Codex 模型目录。现行实现对模型目录中的
`supported_reasoning_levels` 统一写入空列表，导致用户选择模型后看不到可选思考
深度。把空列表理解为“让 Codex 自动发现所有档位”并不可靠：空列表表达的是
GPTEasy 没有声明能力，实际选择器是否显示档位取决于当前 Codex 版本和目录加载
路径。

本机对 Codex 0.160.0/0.160.1 的隔离 `model/list` 差分验证得到以下事实：

1. 完全不指定 `model_catalog_json` 时，Codex 对自身内置认识的模型能够返回推理档位。
2. GPTEasy catalog 条目删除 `supported_reasoning_levels` 后，Codex 整体退回内置
   目录，而不是逐条为自定义条目补全能力。
3. 当前 GPTEasy catalog 中的模型全部为能力空列表时，`gpt-6.1-sol` 也不会显示
   可选档位。
4. 人工构造档位可以验证客户端选择器链路，但不能证明供应商真实支持这些档位。

因此，本方案不选择“全部交给空字段自动推断”，也不选择“仅按模型名称伪造
`low/medium/high`”。目标是把可信能力、供应商声明和兼容猜测严格分层，并让
Codex 升级带来的新模型元数据可以被利用。

## 2. 设计目标

- 对 Codex 已知模型尽可能复用 Codex 当前版本的可信元数据。
- 新模型被当前 Codex 内置目录认识后，GPTEasy 不需要为每个模型发布硬编码更新。
- 保留 GPTEasy 对第三方供应商模型的目录筛选和路由能力。
- 不把模型 ID、模型名称、供应商名称或 `/models` 返回结果当作推理能力证据。
- 将“选择器可选范围”和“当前配置实际生效的 `model_reasoning_effort`”分离。
- Windows、WSL2、Bash 和 Zsh 使用同一套能力决策结果，不在 shell 中重新猜测。
- 未知、冲突或探测失败时宁可明确降级，也不静默显示未经验证的档位。
- 诊断证据能够区分内置元数据、显式供应商声明、厂商兼容兜底和未知状态。

## 3. 非目标

本方案不处理以下问题：

- 为每个供应商实现原生 thinking budget 或 extended thinking 请求格式。
- 通过模型名称推断上下文窗口、工具、图片能力或 Responses 兼容性。
- 合并多个供应商的模型到同一个可路由的全局目录。
- 自动升级 Codex 或依赖未来尚未验证的目录字段语义。
- 在本方案中修改 OpenAI 登录模式、供应商验证闭环或凭据存储。
- 在本方案中直接改变默认生效值的既有官方映射；生效值仍受 ADR-0051 约束。

## 4. 核心概念和不变量

### 4.1 三种数据不能互相冒充

| 数据 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 供应商模型发现列表 | 供应商列出了某个模型 ID | Codex 元数据、工具、上下文或推理能力 |
| Codex 内置模型元数据 | 当前 Codex 版本对精确模型 ID 的已知描述 | 第三方供应商端点一定实现该能力 |
| 供应商显式能力声明 | 供应商对指定模型/协议作出的声明 | Codex 客户端一定支持对应档位 |

### 4.2 能力来源必须可追溯

每个 `supported_reasoning_levels` 结果都必须带有内部来源分类和规则标识，至少区分：

- `codex_builtin`：当前 Codex 元数据对精确模型 ID 的结果；
- `provider_declared`：用户或供应商针对精确模型的显式声明；
- `vendor_compatibility`：显式启用的厂商/协议兼容规则；
- `unknown`：没有足够证据；
- `conflict`：来源之间不一致，必须按冲突策略处理。

来源和规则标识用于日志、测试和诊断，不得写入 Codex 不认识的自定义字段，避免
破坏目录 schema。

### 4.3 精确匹配优先

能力合并只能将精确模型 ID 作为默认匹配键。复用供应商发现流程已有的输入校验，保留 ID 的
大小写和完整内容；不得额外去掉版本后缀、展开别名或进行家族匹配。不得把前缀、
家族名或模糊包含关系当作精确匹配。
模型名称包含 `gpt`、`deepseek`、`o` 等字符串本身不构成精确匹配证据。

## 5. 总体方案：可信元数据优先，显式兜底其次

模型目录生成增加一个内部“能力解析”模块。它对外只提供一个小接口：输入当前
Codex 环境、当前活动供应商的模型集合和可选策略，输出每个模型的目录能力、来源
和诊断原因。具体实现可拆为多个 adapter，但调用方不应分别处理 Windows、WSL2
和 Linux 的优先级逻辑。

推荐决策顺序：

```text
Codex 精确模型元数据
    ↓ 无结果
精确模型的供应商显式声明
    ↓ 无结果
显式启用的厂商/协议兼容规则
    ↓ 无结果
未知能力（不伪造范围）
```

### 5.1 Codex 内置元数据

后续实现应设计一个隔离的 Codex 元数据读取 adapter。它需要在不读取凭据、不调用
真实供应商、不创建用户会话的前提下，取得当前 Codex 版本的内置模型列表及其推理
档位。

重要约束：当前活动供应商的自定义 `model_catalog_json` 可能覆盖或替代 Codex
默认目录，因此不能把加载 GPTEasy catalog 后得到的空能力结果当作 Codex 内置
元数据。实现应采用下列原则之一，并先通过实际捆绑 Codex 版本验证：

- 使用不加载 GPTEasy catalog 的隔离 Codex 元数据探测；或
- 使用 Codex 官方提供的独立元数据入口；或
- 使用经版本绑定、可验证的 Codex 内置元数据副本。

首选运行时探测，避免 GPTEasy 自己维护精确模型名单。探测失败、协议不兼容或
Codex 不认识该模型时，必须进入下一层，而不是把失败当成“所有档位可用”。

该 adapter 必须是只读、限时、可取消和无凭据的。不得启动真实供应商请求，不得
重启用户 Codex，不得修改用户配置。探测结果应绑定 Codex 可执行文件版本或等价
版本指纹，避免把一个版本的元数据静默用于另一个版本。

`model/list` 只提供选择器需要的部分元数据，不等于完整 catalog 条目。不得因此把
返回的选择器对象直接作为 catalog 写入，也不得复制它没有提供的上下文、工具等
能力。推理档位与默认档位经版本 adapter 转换；其他字段继续遵守既有目录契约，
不在本次设计中无条件继承内置模型的全部能力。

探测必须分页读取完整 `model/list`，限制页数、模型数量和响应大小。建议总超时
10 秒，子进程清理上限 2 秒；最终参数应经平台测试固定并集中管理。禁止无限等待、
输出原始 stderr 或把探测失败误判为模型不存在。隔离临时目录使用私有权限，清理
只涉及本次创建的目录和自有子进程。

### 5.2 供应商显式声明

对于第三方供应商或 Codex 内置目录尚未认识的模型，允许未来增加精确模型级声明。
声明必须绑定供应商不可变 ID、验证组合指纹、精确模型 ID和声明版本；供应商配置
变化后不得无条件沿用旧声明。重新验证时，只有绑定仍一致且本次发现仍包含该模型
才可显式保留声明；来源或规则变化时必须重新确认。

声明应能表达：

- 支持的 Codex effort 集合；
- 默认 effort（若有）；
- 声明来源、版本和更新时间；
- 声明是供应商官方文档、供应商验证返回，还是用户手动确认。

供应商 `/models` 列表不能自动生成这类声明。默认模型完成 Responses 流式工具
调用闭环，也不能单独证明它支持所有推理档位。

### 5.3 厂商/协议兼容兜底

厂商规则可以作为显式启用的兼容策略，不能作为静默默认能力判断。规则的匹配
身份应优先使用供应商协议或已确认厂商身份；模型名称只可作为用户确认后的辅助
配置，不能直接决定能力。

每条规则至少包含：

- 规则 ID和版本；
- 匹配条件及其优先级；
- 允许声明的 effort 集合；
- 默认生效 effort（如有）；
- 官方出处和发布日期；
- 适用 Codex 版本范围；
- 服务端拒绝某档位时的失败/降级策略。

规则必须明确标记为“兼容声明”，不能伪装成 `codex_builtin`。界面和日志应能够
告诉用户该范围不是当前模型的实测能力。

建议第一阶段只提供规则框架和配置入口，不默认启用宽泛的 OpenAI、DeepSeek
名称匹配。若将来启用某厂商规则，必须先有独立的官方兼容证据和真实供应商验收。
同厂商不同模型支持范围不同的情况，必须允许精确模型声明覆盖厂商规则。

### 5.4 未知和冲突

没有可信来源时，能力状态为 `unknown`。不得用空数组传递“无限制”的含义，也
不得因当前根级 effort 是 `high` 就生成 `high` 范围。

优先级表示“缺失时去哪一层取值”，不是忽略供应商已知限制：

- Codex 已知范围为候选；若同时存在有效的供应商精确声明，按声明约束取交集，
  防止代理端点不支持 Codex 的全部范围；记录双方来源和裁剪原因。
- 供应商声明包含 Codex 当前版本不能表达的 effort 时，不把它强行加入 catalog。
- 厂商规则只填补没有精确来源的模型，不扩张或覆盖已有精确范围。
- Codex 精确元数据若明确声明空范围，是一个已知结果，不能自动触发厂商兜底；
  它与“没有找到这个模型”或“探测失败”不同。
- 交集为空且一方要求非空、声明默认值不在有效集合等情况是 `conflict`，不能静默
  改成最高档或固定 `high`。目录草案报告冲突，要求修正声明后再提交。

根级实际 effort 与有效选择范围不一致时也必须输出独立诊断。对用户本次要求写入
的受管值发生已知不兼容，配置准备阶段失败，保留上一份状态；不擅自改档位。

## 6. Codex catalog 的生成策略

### 6.1 不把“省略字段”当作通用 fallback

在当前实测版本中，catalog 条目省略 `supported_reasoning_levels` 会导致 Codex
退回内置目录整体行为，并不会为 GPTEasy 的自定义条目逐个补全。因此后续实现
必须先针对项目实际捆绑 Codex 版本验证 schema 和选择器行为，再决定字段如何序列化。

实现不能依据字段名称猜测以下任一语义：

- 字段省略等于无限制；
- 空数组等于无限制；
- `null` 等于由客户端继承；
- 自定义 catalog 条目会自动继承内置条目。

### 6.2 推荐的目录输出分支

能力解析完成后，目录渲染器根据当前 Codex 版本契约选择输出分支：

1. 对已知且可安全复用的 Codex 元数据，生成当前供应商所需的自定义条目，并
   保留 Codex 允许的完整能力范围。
2. 对有供应商声明或兼容声明但 Codex 不认识的模型，仅在 schema 明确支持时
   写入该声明；同时保留来源标记在 GPTEasy 内部，不写未知扩展字段。
3. 对未知能力，使用经过实际版本验证的未知模型表示；若当前版本没有安全表示，
   则阻止提交并说明版本不兼容，不生成一个语义不明的目录。

**第一阶段采用明确的未知模型降级：** 在已经验证允许空范围的 Codex 版本中，
未知模型仍可进入供应商目录，使用 `default_reasoning_level: null` 和
`supported_reasoning_levels: []`，因此暂时没有思考深度选项。这是明确的未知状态，
不是本次修复要彻底禁止所有空数组；本次禁止的是“已知模型也统一变成空数组”。
不为修复一个未知模型而删除整个 catalog，避免暴露供应商没有列出的模型。

目录渲染失败、schema 不兼容或结果无法区分未知与无限制时，切换必须失败并保留
上一份目录、配置、凭据和数据库状态。

### 6.3 根级实际 effort

`model_reasoning_effort` 继续只表示当前默认模型请求实际使用的 effort，不表示
选择器范围。其决策沿用 ADR-0051 的有官方依据映射：

- Codex/供应商的精确官方映射优先；
- 没有可靠映射时不按名称猜测；
- 未知时保留为空或采用供应商官方要求的兼容配置；
- 供应商切换、WSL2 和 Linux 导出复用同一计算结果。

用户之后在 Codex 选择另一个模型时，不能把此前写入的根级值解释为新模型已完成
能力验证。若未来需要模型选择后自动重算，必须另行设计 Codex 事件/配置生命周期。

## 7. 各环境实现边界

### 7.1 Windows

Windows 是首选的运行时能力发现环境。后续实现可以由 Rust 后端调用隔离的 Codex
adapter，生成当前活动供应商 catalog，再按现有原子写入、备份、Saga 和 daemon
刷新流程提交。

探测不得读取 `auth.json`，不得把 API Key 放到命令行或日志，不得调用真实供应商，
不得重启用户 Codex。探测失败不能阻断仅依赖已有可信声明的显示，但目录生成无法
安全表达能力时必须阻断配置提交或明确要求用户选择策略，不能生成半成品。

### 7.2 WSL2

WSL2 不应在探测阶段启动停止的发行版。若发行版正在运行，应使用该发行版实际
拥有的 Codex 版本和配置上下文；若需要用户明确授权启动，必须沿用现有 WSL2
生命周期和恢复规则。

Windows 端发现的 Codex 元数据不能直接假设适用于 WSL2 中另一版本的 Codex。能力
结果至少绑定目标环境的 Codex 版本；无法读取时使用供应商显式声明或未知状态。

### 7.3 独立 Linux 导出

导出物不能依赖 Python、Node、GPTEasy 可执行文件或第三方解析器。推荐在 GPTEasy
导出阶段完成能力解析，把脱敏的能力结果和来源作为 Linux 供应商快照的一部分
写入导出物；Bash/Zsh 只消费快照，不重新按模型名称判断。

导出元数据属于版本化快照，不承诺目标 Linux Codex 升级后自动更新。快照记录来源
Codex 版本、目录契约版本和生成时间；目标版本不在已验证兼容范围时，明确警告或
拒绝不兼容输出，不能声称已经对目标版本完成探测。第一阶段只读检查目标版本，
不在 shell 内实现 JSON-RPC 解析。重新导出是第一阶段更新快照的方式。

因而“升级 Codex 无需发布 GPTEasy 即可获得新增模型能力”首先适用于运行时探测
可用的环境；Linux 静态导出仍需更新快照。它也不保证所有未来 Codex schema 无需
GPTEasy 适配。

若未来要求 Linux 主机自行刷新 Codex 内置元数据，必须另行设计仅依赖系统已有的
Codex 官方接口，并保持 source 导出脚本零写入和最小 shell 写入协议；本方案不把
该能力作为第一阶段要求。

## 8. 数据与生命周期设计

### 8.1 结果模型（概念）

后续实现应拥有等价于以下概念的数据，而不要求直接采用这些字段名：

```text
ReasoningCapability {
    levels: ordered set<effort>,
    default_level: optional<effort>,
    source: codex_builtin | provider_declared | vendor_compatibility | unknown | conflict,
    source_id: stable rule/profile identifier,
    codex_version: optional<version fingerprint>,
    observed_at: timestamp,
    confidence: verified | declared | compatibility | unknown
}
```

实现还应区分 `known_nonempty`、`known_empty`、`not_found`、`probe_failed` 和
`conflict`，不能只靠 `levels=[]` 判断状态。默认值必须属于有效范围，否则置为空
或报告冲突（来源确实要求该值时）。保留来源给出的排序，不按字母排序努力档位，
不默认选择最高档。

未来档位不应被 GPTEasy 固定的四档枚举无声丢弃。保存可追溯的字符串值，经过目标
Codex 版本的配置/catalog 契约 adapter 校验后才允许输出；目标客户端不认识时
报告 `unsupported_effort`，不自动改写成旧档位。`none` 字符串与“省略根级字段”
不同，不能把字符串 `none` 当成空值处理。需要检查现有
`src-tauri/src/provider/reasoning.rs` 的四档校验，但本次不修改该代码。

该结果属于模型目录生成的中间数据，不应把 API Key、完整供应商配置或原始响应写入
catalog、日志或 Linux 快照。

### 8.2 缓存

可以缓存只读的 Codex 元数据探测结果，但缓存必须绑定：

- Codex 可执行文件版本或内容指纹；
- 元数据 schema 版本；
- 目标环境；
- 探测完成时间和结果分类。

Codex 升级、schema 变化、探测失败或用户明确刷新时必须重新验证缓存。缓存不能
成为永久的 GPTEasy 模型硬编码名单。

### 8.3 迁移和旧目录

现有由 GPTEasy 生成的空能力目录以及旧版固定三档目录均不能被当作可信能力证据。
迁移应遵循：

- 应用启动不静默改写用户目录；
- 用户明确重新应用供应商或确认迁移后才生成新目录；
- 能严格证明是 GPTEasy 未被外部修改的旧模板时，才允许迁移；
- 外部修改、来源不明或 schema 不兼容时保留原文件并转为人工处理；
- 目录、配置、凭据和数据库状态继续纳入现有备份、并发检查、原子写入和失败恢复。

## 9. 诊断、日志和隐私

为区分当前问题，至少记录以下阶段和分类：

- `reasoning_metadata.inspect`
- `reasoning_metadata.codex_probe`
- `reasoning_metadata.provider_declaration`
- `reasoning_metadata.vendor_fallback`
- `reasoning_metadata.conflict`
- `reasoning_metadata.unknown`
- `reasoning_metadata.render`
- `reasoning_metadata.commit`

每条证据记录：操作 ID、目标环境、脱敏供应商 ID、脱敏模型 ID、Codex 版本摘要、
规则 ID、来源分类、结果分类和稳定 message ID。禁止记录 API Key、完整 config、
完整命令行、控制 socket 原文、供应商响应正文和请求内容。

诊断必须能回答：

1. Codex 是否认识这个精确模型 ID？
2. 选择器范围来自哪一个来源？
3. 是否启用了厂商兼容兜底？
4. 空范围是未知、schema 限制还是写入失败？
5. 目录已提交但 Codex 消费者尚未重启，还是目录本身没有生效？

## 10. 分阶段实施计划

### 阶段一：契约和探测验证

- 针对项目捆绑的 Codex 版本验证独立内置元数据探测方式；
- 确认 `model/list`、TUI 选择器和 `model_catalog_json` 的版本相关行为；
- 建立 Windows 隔离探测 adapter 的接口和假数据测试；
- 明确 unknown、conflict、not available 的序列化契约；
- 不启用厂商名称推断。

### 阶段二：可信元数据合并

- 将 Codex 精确元数据合并到当前供应商目录；
- 保留供应商自定义模型的目录筛选能力；
- 以版本绑定缓存降低重复探测；
- 接入现有 Windows 配置 Saga、诊断日志和模型目录刷新流程；
- 完成未知模型、Codex 已知模型和 provider-only 模型的回归测试。

### 阶段三：跨环境一致性

- 将能力结果传递到 WSL2 和 Linux 导出快照；
- 验证不同 Codex 版本不共享错误缓存；
- Bash/Zsh 只消费快照，不重复推断；
- 覆盖导出后手工修改、恢复点和失败回滚。

### 阶段四：显式供应商声明和可选兼容规则

- 先实现精确模型/供应商声明的数据结构；
- 只有取得官方证据后再添加具体厂商规则；
- 厂商规则默认关闭或需要用户明确启用；
- 对规则产生的档位显示“兼容声明，未由当前模型验证”；
- 通过真实供应商请求验收服务端拒绝和降级行为。

## 11. 验收标准

### 必须通过

- Codex 已知的精确模型能够在不被 GPTEasy 空能力覆盖的情况下显示其当前版本
  支持的选择范围。
- Codex 升级后新增的已知模型无需 GPTEasy 发布精确模型名单更新即可被识别。
- Codex 不认识的 provider-only 模型不会因模型名称自动获得推理档位。
- 空数组、字段省略和 `null` 的语义均有当前 Codex 版本证据，不依赖猜测。
- 选择器范围和根级实际 effort 在数据、日志和测试中分离。
- Windows、WSL2、Bash、Zsh 对同一快照使用相同能力决策，不在 shell 中按名称推断。
- 探测、渲染或提交失败不会留下半成品配置或 catalog。
- 日志可以区分来源、未知、冲突、写入失败和消费者尚未重启。
- 不读取或泄露 API Key、完整配置和真实供应商响应。

### 厂商兜底启用前必须额外通过

- 有可追溯的官方兼容定义和规则版本；
- 精确模型声明可以覆盖厂商规则；
- 同厂商不同模型的能力差异有测试覆盖；
- 服务端拒绝不支持档位时，用户获得可理解且可重试的结果；
- UI 明确显示这是兼容声明而非已验证能力；
- 至少完成一个真实供应商的 Responses/Codex 端到端验收。

## 12. 测试矩阵与交接位置

| 场景 | 必须验证的结果 |
| --- | --- |
| 已知精确 ID，原目录为空 | 合并后范围与隔离 Codex 来源一致；真实选择器显示档位 |
| 新 Codex 增加模型 | 旧版本缓存失效，读取新范围，不需要新增 GPTEasy ID 分支 |
| 纯测试未来 ID / provider-only ID | 没有精确来源时保持未知，不因名称生成档位 |
| Codex 已知空范围 | 不触发厂商兜底，与未发现模型有不同日志 |
| Codex/供应商范围不一致 | 按声明约束取交集；冲突时不提交 |
| 多页 model/list / 超时 / 异常退出 | 全量或明确失败；无残留自有进程；用户文件不变 |
| 新 effort 字符串 | 客户端认识时可保留，不认识时明确失败；无四档静默裁剪 |
| 修改 default 或根级 effort | 不凭默认值补造范围；已知不兼容有独立诊断 |
| 同名模型来自不同供应商 | 只输出当前供应商，声明和快照不串用 |
| Windows/WSL Codex 版本不同 | 不复用另一环境的缓存，WSL 停止时不偷偷启动 |
| Linux Bash/Zsh | source 零写入；同快照输出相同；无新增运行时依赖 |
| 目录写入失败 / 外部目录变更 | 原子恢复或要求重新确认，不覆盖外部修改 |
| daemon 刷新失败 | 不回滚已提交配置，与能力发现失败分开反馈 |
| 敏感值哨兵测试 | 日志、错误、导出诊断无凭据和原始响应 |

实现位置建议（以实施时实际代码为准）：

- `src-tauri/src/provider/model_catalog.rs`：接收能力解析结果，避免全部未知模板覆盖。
- `src-tauri/src/provider/reasoning.rs`：保持生效值与范围独立，检查未来 effort 校验。
- `src-tauri/src/environment.rs`：原生环境配置准备和 Saga 集成。
- `src-tauri/src/wsl.rs`：目标 Codex 版本约束和既有生命周期。
- `src-tauri/src/provider/linux_export.rs`、`shell_runtime.sh`：快照传递、版本提示，
  不在 shell 中做厂商推断。
- `scripts/diagnose-reasoning-selector.py`：仅作为开发诊断证据，不成为产品或 Linux
  导出运行时依赖。可扩展隔离矩阵，但必须另补产品代码自动回归测试。
- `docs/testing/`：实施记录与真实 CLI/桌面选择器验收；分别标记已通过和未执行。

**推荐首个可交付范围：** 完成阶段一至三的可信精确元数据合并、未知降级和跨环境
快照；第四阶段保留为后续工作，不要求为了修复当前空选择器立即新增厂商推断 UI。

## 13. 实施前需要验证的技术问题

1. 当前捆绑 Codex 版本是否存在稳定、无凭据的内置元数据读取入口？
2. 如果只能通过隔离 app-server 读取，如何在不启动用户 daemon 的前提下完成探测和
   生命周期清理？
3. 自定义 provider-only 模型怎样在保留供应商目录的同时复用内置模型元数据？
4. 当前 Codex 版本对未知能力有没有官方的“不收窄范围”表达？若没有，产品是否
   接受未知模型暂时没有选择器档位？
5. 供应商显式声明存放在验证快照、供应商配置还是单独版本化规则文件？
6. 厂商兼容规则是否默认关闭，还是仅对用户明确选择的供应商启用？
7. Linux 导出快照需要在导出时固定 Codex 版本元数据，还是允许用户手动刷新？
8. 未来模型选择后自动重算根级 effort 是否需要 Codex 事件支持，还是继续要求用户
   明确应用配置？

## 14. 与现有 ADR 的关系及实施边界

本文件是规划，不宣称现有实现已具备这些能力，也不直接取代 accepted ADR。

- ADR-0049 的供应商筛选、验证快照与安全写入约束保持不变。
- ADR-0051 的生效值/范围解耦、不按名称伪造能力保持不变；补充“已知模型应动态
  保留 Codex 范围，未知模型可以显式空范围”的实现路径。
- 厂商兼容声明是相对 ADR-0049/0051 的**待议扩展**。第四阶段实施前必须新增 ADR
  或修订相关条款，并更新 `CONTEXT.md`，不能在旧文档禁止范围内静默实现。
- 默认生效 effort 的官方映射不是本次厂商范围兜底，不得混用。

后续实现会话可以修改代码、测试和实现记录，但必须先以本方案为设计输入，并在
发现 Codex 版本契约与本方案不一致时先更新方案或新增 ADR。不得直接把厂商名称
判断散落到 Windows、WSL2、Linux 三套分支中，也不得以“让选择器显示”为理由把
未知能力改写成固定 `low/medium/high`。
