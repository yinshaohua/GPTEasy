# Feature Research

**Domain:** 跨平台桌面伴侣程序、Codex API 供应商管理与多受管环境切换
**Project:** GPTEasy
**Researched:** 2026-08-05
**Confidence:** HIGH

## 研究范围与判断原则

本文件只把已经锁定的 GPTEasy v1 范围整理成可实施的能力分组、依赖关系和可观察验收行为，不重新讨论产品定位、UI 方向或架构决策。`PROJECT.md`、`CONTEXT.md`、`docs/adr/0001-0008` 和 `docs/ui/UI-SPEC.md` 是本项目的权威基线；外部官方资料只用于核对实现路径，不覆盖这些基线。

“复杂度”表示实现和验收的综合难度，而不是代码行数：

- **LOW**：边界清楚，主要是局部 UI 或常规状态读写。
- **MEDIUM**：需要跨组件或跨平台协调，但失败面有限。
- **HIGH**：涉及凭据、文件原子性、进程生命周期、跨环境一致性、脚本安全或升级恢复。

首版采用一次完整交付策略。下面的能力分组可以作为实施阶段顺序，但任何只完成部分能力的中间阶段都不是正式 v1 发布物。

## Feature Landscape

### Table Stakes（用户预期能力）

这些能力是 GPTEasy 的首版完成基线。用户不会因为它们存在而额外认可产品，但缺失其中任何一组，核心价值就无法成立。

| ID | 能力 | 为什么是预期能力 | 复杂度 | 实施要点 |
|----|------|------------------|--------|----------|
| TS-01 | 本地应用状态与供应商目录 | 用户需要关闭并重新打开应用后仍看到供应商、验证状态、环境选择和设置 | HIGH | Rust 后端独占访问用户级 SQLite；API Key 明文保存是锁定决策；React 只能通过受控 Tauri command 访问 |
| TS-02 | 不可变供应商 ID与 DayWay 生命周期 | 供应商改名、改地址或换 Key 后，原生 Codex 环境和 WSL2 环境仍需指向同一个供应商身份；DayWay 必须有稳定的内置推荐入口 | HIGH | 区分供应商 ID 与可变资料；未配置推荐供应商始终在设置列表第一，但不能出现在托盘或成为当前供应商 |
| TS-03 | 标准供应商配置 | 用户至少需要填写服务地址、API Key 和默认模型 | MEDIUM | 首版不增加自定义 Header、组织或项目标识等高级认证字段；远程服务地址必须是 HTTPS，只有回环地址可使用 HTTP，且无绕过开关 |
| TS-04 | 模型获取与供应商验证 | “能连通”不足以证明 Codex 可用，用户需要知道默认模型和 Codex 所需能力都经过验证 | HIGH | 依次完成默认模型确认、Responses API 流式响应、工具调用闭环；失败停止后续步骤 |
| TS-05 | 验证后保存与编辑生命周期 | 未验证配置不能进入可切换目录；修改关键字段失败时不能破坏原来的可用配置 | HIGH | 地址、API Key 或默认模型修改后必须重新验证；失败继续保留旧的已验证配置；只修改名称等不影响服务能力的字段可不重新验证 |
| TS-06 | 原生 Codex 环境检测 | 用户需要知道 GPTEasy 是否能管理当前用户的原生 Codex 环境 | HIGH | 将统一 ChatGPT 桌面应用中的 Codex 与本机原生 Codex CLI 视为同一个原生 Codex 环境；只管理当前用户默认配置 |
| TS-07 | 原生环境直接切换 | 核心价值是切换实际 Codex 配置，而不是只在 GPTEasy 内改变一个选择 | HIGH | 直接配置模式写入原生 Codex 配置；代理 API 模式为默认模式；原厂登录模式由用户在设置中主动启用 |
| TS-08 | 配置保留、备份、原子写入与失败恢复 | 切换 API 服务不能重置用户已有 Codex 设置，也不能因写入中断留下半份配置 | HIGH | 写入前创建带时间戳备份，使用临时文件和原子替换，只修改 GPTEasy 管理字段；失败停止并提供恢复路径，默认每个环境保留最近五份 |
| TS-09 | 进程感知与待重启 | 直接配置模式不会改变已经加载旧配置的运行中 Codex 进程 | HIGH | 识别桌面 Codex 和本机 Codex CLI；运行中切换先让用户选择立即重启、稍后重启或取消；稍后重启显示待重启状态，不自动终止进程 |
| TS-10 | 托盘优先的原生环境快捷切换 | 供应商切换是高频动作，用户不应每次都打开设置窗口 | MEDIUM | 托盘只切换原生 Codex 环境的已验证供应商，不提供 WSL2 快捷操作；当前供应商、原厂登录模式、外部配置和待重启状态必须可见 |
| TS-11 | Windows WSL2 独立管理 | Windows 用户的 WSL2 Codex 配置与原生 Codex 环境分离，每个发行版可能使用不同供应商 | HIGH | 发现各 WSL2 环境及其默认用户；逐环境选择或批量切换；不扫描或管理发行版内其他用户 |
| TS-12 | 独立 Linux 切换脚本 | 用户复制脚本后仍应能在没有 GPTEasy 的 Linux 系统上长期切换供应商 | HIGH | 导出当前全部已验证供应商的 Bash 4+ 或 Zsh 5+ function；脚本自包含明文凭据，只修改 Linux 用户级 Codex 配置中的 GPTEasy 管理区块 |
| TS-13 | 供应商更新传播与删除保护 | 同一个供应商可能被多个受管环境使用，资料更新后不能产生环境间隐性分叉 | HIGH | 已验证供应商更新自动传播到所有当前使用它的原生 Codex 环境和 WSL2 环境；仍被任一受管环境使用的供应商不能直接删除 |
| TS-14 | 外部配置共存 | 用户可能在 GPTEasy 外部修改默认 Codex 配置，GPTEasy 不能把未知状态误判为自己的供应商 | HIGH | 能唯一匹配才关联 GPTEasy 供应商；无法匹配的状态作为外部配置展示，不自动覆盖、不视为已验证供应商 |
| TS-15 | SQLite 永久顺序迁移 | 桌面应用升级不能要求用户清空供应商和凭据重新开始 | HIGH | 迁移前完整备份并默认保留最近三份；迁移在事务中执行；失败回滚且拒绝继续运行；发现更高版本数据库时拒绝写入 |
| TS-16 | 脱敏诊断与用户控制的运行维护 | 非技术用户需要可提交的排障资料，但明文 API Key 不能进入日志或自动上传 | MEDIUM | 本地诊断日志默认保留最近七天；诊断导出由用户主动触发且不含凭据；更新检查启动后每天最多一次，下载和安装均需用户确认 |
| TS-17 | 托盘驻留、首次使用和空状态 | 桌面伴侣的基本生命周期必须可理解，缺少宿主应用或供应商时不能出现无意义空白 | MEDIUM | 关闭设置窗口默认驻留托盘；首次关闭提示；首次启动进入供应商页面而非向导；所有空状态提供明确下一步 |
| TS-18 | 跨平台发布与可访问界面 | v1 的承诺包含 Windows、macOS、中文和英语，核心操作不能只对鼠标用户可用 | HIGH | Windows 10 22H2+ x64/ARM64、macOS 14+ Intel/Apple Silicon；支持浅色/深色/系统主题、键盘、屏幕阅读器、200% 缩放、高对比度和减少动态效果 |

### Differentiators（锁定范围内的差异化）

这些不是所有配置工具都会提供的能力，但正是 GPTEasy 在已锁定范围内的竞争优势。它们不是可随意删减的“锦上添花”，而是应在完整 v1 验收中体现的差异化。

| ID | 差异化能力 | 用户价值 | 复杂度 | 验收关注点 |
|----|------------|----------|--------|------------|
| D-01 | 三项供应商验证闭环 | 用户保存的是“Codex 实际可用”的供应商，而不是只完成一次普通 HTTP 请求的地址 | HIGH | 三项检查按固定顺序执行；任一失败停止；只有三项均成功才进入已验证供应商目录 |
| D-02 | 一个供应商目录、多个独立受管环境 | 供应商资料只维护一份，原生 Codex 环境、各 WSL2 环境和导出 Linux function 可分别选择当前供应商 | HIGH | 改供应商资料后传播到引用它的环境；改变某个环境的当前供应商不改变其他环境 |
| D-03 | 直接配置而非本地 API 代理网关 | GPTEasy 不必持续驻留在每一次 Codex 请求链路中，导出的 Linux function 也能脱离桌面程序工作 | HIGH | 受管配置直接变化；运行中的 Codex 明确进入待重启；系统中不存在必须持续运行的本地网关依赖 |
| D-04 | 可恢复的切换安全边界 | 用户能在不丢失既有 Codex 配置的前提下尝试切换，失败不会变成静默破坏 | HIGH | 备份、临时文件、原子替换、保留非 GPTEasy 配置和失败恢复在宿主、WSL2、Linux 三条路径上行为一致 |
| D-05 | 外部配置的非破坏识别 | 用户可以先继续使用外部配置，再决定是否重新验证并纳入 GPTEasy，不会被工具强制接管 | HIGH | 未知配置显示为外部配置；刷新或切换不会把它默默改成某个同名供应商 |
| D-06 | 不可变身份支撑的更新传播 | 更换名称、地址或 Key 不会让环境引用断裂，也避免同名供应商互相覆盖 | HIGH | 供应商 ID 永不改变；匹配优先使用 ID，地址和模型只作为唯一匹配辅助；有引用时更新传播而非重新创建供应商 |
| D-07 | 脱离 GPTEasy 的 Linux function | 用户复制后可在另一台 Linux 上长期使用，且目标机器当前状态由脚本自行读取 | HIGH | 目标 Linux 的当前供应商不继承导出机状态；交互选择可退出不写入；脚本不依赖 GPTEasy、Python、Node.js 或第三方解析器 |
| D-08 | 明文凭据的可理解性与严格脱敏边界 | 非技术用户可以完整查看、复制和独立导出 API Key，同时诊断资料仍不泄露凭据 | HIGH | 新增页默认显示 Key，已保存页默认隐藏但可完整显示/复制；日志、错误、截图辅助和诊断导出均不含 Key |
| D-09 | 进程感知的切换决策 | 用户能在“立即生效”和“不中断当前任务”之间做明确选择，而不是被静默终止 | HIGH | 重启前展示当前/目标供应商、运行中的 Codex 类型和中断警告；取消发生在写入前；稍后重启有托盘可见状态 |
| D-10 | 非技术用户的托盘优先体验 | 高频切换路径短，技术细节仍可按需展开，不把产品变成开发者管理面板 | MEDIUM | 设置窗口无独立仪表盘；托盘菜单只承担原生环境切换；状态同时使用图标和文字；错误默认给简短说明、技术详情可展开 |
| D-11 | WSL2 停止状态保留 | 管理 WSL2 不会把用户原本停止的发行版永久变成运行状态 | HIGH | 对已停止发行版操作前提示临时启动；成功或失败处理完成后恢复原有停止状态；单个发行版失败不掩盖批量结果 |

### Anti-Features（明确排除）

以下项目可能具有表面吸引力，但与本版的本地、可恢复、直接配置边界冲突。需求、设计和验收都不应把它们作为“顺手补上”的默认扩展。

| 反功能 | 为什么有人会要求 | 为什么必须排除 | 替代做法 |
|--------|------------------|------------------|----------|
| 产品账户、云端存储、云同步 | 多设备自动出现同一套配置 | 明文凭据进入服务端和同步链路，违背本地模式并引入运营与恢复责任 | 本机 SQLite；跨设备由用户自行处理，Linux 通过手工复制导出脚本 |
| 自动跨设备迁移、脚本回导 | 想快速复制整个目录 | Linux 脚本是独立使用物，不是 GPTEasy 的回导格式；回导会模糊凭据和身份边界 | 重新配置并验证供应商；保留不可变供应商 ID 的本机生命周期 |
| Linux 独立 GUI | 希望三端都有相同界面 | 首版 Linux 交付物明确是 shell function，不应增加另一套 GUI、打包和状态同步系统 | 导出 Bash 4+ 或 Zsh 5+ 的自包含 function |
| 本地 API 代理网关 | 想避免修改 Codex 配置 | 会使 GPTEasy 变成持续请求依赖，破坏 Linux 脱离运行和直接配置模式 | 直接修改受管配置；对运行中的 Codex 给出待重启状态 |
| 机器级公共配置、其他用户配置、自定义配置路径 | 想覆盖更多用户或特殊安装 | 权限、路径、所有权和误修改范围不可控；不符合“当前用户配置”边界 | 只管理当前操作系统用户的默认 Codex 配置；WSL2 只管理每个发行版默认用户 |
| WSL2 自动跟随原生环境或托盘快捷切换 | 想一次操作所有环境 | 原生 Codex 环境与每个 WSL2 环境是独立受管环境，自动同步会覆盖用户的独立选择 | 在 WSL2 页面逐个或经确认批量切换 |
| Fish、Nushell、仅 POSIX sh 或运行时依赖脚本 | 想覆盖更多 Shell | 需要不同语法、解析和依赖分发，扩大脚本安全面；超出受支持 Shell | 只生成 Bash 4+ 或 Zsh 5+、无额外运行时依赖的脚本 |
| 无 Key 的脚本导出模式 | 想减少泄露风险 | 脚本无法脱离 GPTEasy 长期完成供应商切换，与锁定的独立 function 目标冲突 | 明确显示明文 Key 风险；复制/保存前固定警告；日志和诊断继续脱敏 |
| 自定义 Header、组织或项目标识 | 想兼容更多供应商 | 会把标准供应商扩展成不受控的认证/路由配置面，增加验证矩阵 | 首版只支持服务地址、API Key 和默认模型 |
| 管理旧版宿主应用供应商 | 想覆盖历史应用 | 旧版宿主应用的配置语义和兼容性不是 v1 目标 | 只检测其存在并提示迁移，不写入其供应商配置 |
| 自动终止 Codex 进程 | 想让切换立即生效 | 可能中断用户任务并造成数据损失；不符合用户决定重启的边界 | 运行中切换先确认立即重启、稍后重启或取消；不自动终止 |
| 持续供应商健康监控、实时在线状态 | 想持续知道供应商是否可用 | 验证时间不是实时健康度；持续请求会引入隐私、网络和后台任务负担 | 展示最近一次完整供应商验证时间；需要时由用户重新验证 |
| 覆盖未知配置或自动修复歧义文件 | 想让配置“看起来统一” | 会破坏外部配置、用户其他设置或无法安全解析的文件 | 展示外部配置；GPTEasy 管理区块损坏、重复或歧义时停止修改并报告 |
| 静默下载、安装或更新 | 想减少操作步骤 | 本地工具不应在用户不知情时改变应用和运行环境 | 每日最多一次检查；发现更新后由用户确认下载和安装 |
| 聊天应用式仪表盘、营销卡片和持续动画 | 想增强视觉吸引力 | 与原生系统工具感、低认知负担和可访问性冲突 | 托盘优先、紧凑卡片、状态图标加文字、克制动效 |

## 复杂度与实现依赖

### 能力分层

| 能力层 | 包含能力 | 综合复杂度 | 主要复杂度来源 |
|--------|----------|------------|----------------|
| L0 安全与状态底座 | SQLite、永久顺序迁移、备份、事务、脱敏、受控 Tauri command | HIGH | 数据库升级失败、密钥边界、前后端所有权和恢复路径必须同时成立 |
| L1 供应商目录与验证 | 标准字段、DayWay、不可变 ID、模型获取、三项验证、验证后替换 | HIGH | 网络协议差异、流式和工具调用闭环、草稿与已验证配置的原子替换 |
| L2 配置写入引擎 | 当前用户默认路径、字段保留、备份、临时文件、原子替换、外部配置识别 | HIGH | 跨平台路径/格式、未知配置、文件竞态和失败恢复 |
| L3 原生 Codex 环境 | 桌面应用/CLI 检测、代理 API/原厂登录模式、进程检测、重启状态 | HIGH | 两类进程共享环境但生命周期不同；直接写入后要区分磁盘状态与运行时状态 |
| L4 托盘与设置 UI | 托盘、供应商页、重启确认、首次使用、状态反馈、主题和无障碍 | MEDIUM/HIGH | UI 状态必须准确反映后端事务结果，且 Windows/macOS 行为要符合各自习惯 |
| L5 WSL2 适配器 | 发行版发现、默认用户、临时启动/恢复、逐个/批量切换 | HIGH | Windows 外部命令、跨系统路径、运行状态恢复和逐发行版错误隔离 |
| L6 Linux 导出物 | Bash/Zsh 生成、值转义、交互选择、管理区块、独立备份和原子写入 | HIGH | 导出的是可执行代码且含明文凭据；目标环境不同、区块歧义必须安全停止 |
| L7 运行维护与发布 | 诊断、更新、登录启动、托盘驻留、安装包和跨平台验收 | MEDIUM/HIGH | 当前用户安装隔离、权限、更新失败、版本兼容和多架构发布矩阵 |

### 关键依赖链

```text
L0 安全与状态底座
    ├──requires──> L1 供应商目录与验证
    │                  ├──requires──> L3 原生 Codex 环境切换
    │                  │                  └──enhances──> L4 托盘与设置 UI
    │                  ├──requires──> L5 WSL2 适配器
    │                  └──requires──> L6 Linux 导出物
    ├──requires──> L2 配置写入引擎
    │                  ├──required-by──> L3 原生 Codex 环境切换
    │                  ├──required-by──> L5 WSL2 适配器
    │                  └──required-by──> L6 Linux 导出物
    └──cross-cutting──> L7 运行维护与发布
```

### 依赖说明

- **供应商验证 requires 供应商草稿/已验证状态分离：** 地址、API Key 和默认模型的修改必须先进入草稿；完整验证成功后才替换已验证版本。否则失败验证会直接破坏当前环境引用。
- **原生环境、WSL2 和 Linux function requires 共享的供应商身份：** 供应商资料只存一份，环境只保存当前供应商 ID；不能用名称作为主键。
- **所有配置切换 requires 配置写入引擎：** 备份、只改管理字段、临时文件、原子替换和失败恢复不能由三个适配器各自实现一套近似逻辑。
- **原生环境重启提示 requires 磁盘状态与进程状态分离：** “已写入目标配置”不等于“运行中的 Codex 已读取目标配置”；待重启必须是一等状态。
- **WSL2 批量切换 requires 单发行版结果模型：** 批量不是一个全有或全无的布尔操作；每个发行版必须有成功、失败或待重启结果，并能解释停止状态恢复结果。
- **Linux function requires 受限脚本生成器和管理区块解析器：** 生成值的 shell 转义、配置区块识别和歧义停止必须测试同一组边界样本。
- **托盘和 UI requires 后端状态事件：** Toast、系统通知、状态圆点和页面状态只能在后端完成事务或明确失败后更新，不能依据前端乐观状态假定成功。
- **诊断导出 requires 全局脱敏层：** API Key 不能只在某一个日志调用点过滤；错误详情、复制错误、截图辅助、批量结果和导出包都必须经过同一脱敏策略。
- **数据库迁移 requires 历史样本 CI：** 永久顺序迁移的“可升级”必须通过旧版本数据库样本验证，不能只测试空数据库初始化。

### 不应被忽略的内部状态模型

实现需求应显式区分以下状态，避免把它们压扁成一个布尔值：

1. **供应商生命周期状态：** 未配置推荐供应商、草稿、已验证供应商、需要重新验证、删除受阻。
2. **受管环境状态：** 无环境、外部配置、当前供应商、原厂登录模式、待重启、写入失败/恢复中。
3. **WSL2 状态：** 发行版运行/停止、未配置 WSL2 环境、当前供应商、WSL2 待重启、临时启动中、恢复停止失败。
4. **Linux function 状态：** 脚本导出快照、目标 Linux 当前供应商、GPTEasy 管理区块有效/损坏/重复/歧义、写入前备份完成/失败。

### 依赖图

```text
[SQLite 状态、迁移、脱敏与恢复底座]
        ├──requires──> [供应商目录与不可变供应商 ID]
        │                    └──requires──> [模型获取与三项供应商验证]
        │                                           └──enables──> [已验证供应商]
        │                                                             ├──requires──> [原生 Codex 环境切换]
        │                                                             │                  └──enhances──> [托盘切换]
        │                                                             ├──requires──> [WSL2 逐个/批量切换]
        │                                                             └──requires──> [Linux 脚本导出]
        └──requires──> [直接配置写入引擎]
                             ├──required-by──> [原生 Codex 环境]
                             ├──required-by──> [WSL2 环境]
                             └──required-by──> [Linux 用户级配置]

[进程检测与重启状态] ──enhances──> [原生 Codex 环境切换]
[外部配置匹配] ──protects──> [原生 Codex 环境切换]
[供应商更新传播] ──depends-on──> [不可变供应商 ID + 环境引用关系]
[托盘/UI 状态反馈] ──depends-on──> [后端事务结果与状态事件]
[跨平台发布验收] ──depends-on──> [Windows/macOS 适配器 + WSL2 + Linux 生成器]
```

### 依赖驱动的实施顺序

1. 先完成 L0 和 L2，建立不可破坏的数据、配置和恢复边界。
2. 再完成 L1，只有“已验证供应商”存在后，切换、WSL2 和脚本才有合法输入。
3. 完成 L3 后接入 L4；先有可信后端状态，托盘和页面才不会显示假成功。
4. L5 与 L6 可在共享写入引擎和供应商目录稳定后并行实现，但必须分别做 Windows/WSL2 和真实 Bash/Zsh 验收。
5. L7 最后收敛运行维护、安装更新和多平台发布矩阵；它不能替代核心切换路径的验收。

| AC-STATE-01 | 首次创建或修改供应商、环境选择和设置 | 数据保存于用户级 SQLite；关闭并重新打开应用后状态一致；React 无法直接打开数据库文件，只能通过受控 Tauri command 读写 |
| AC-STATE-02 | 使用历史版本数据库直接启动最新版 | 按永久保留的顺序迁移逐步升级；迁移前完整备份，默认保留最近三份；升级后供应商、明文 Key、验证状态和环境引用仍可读 |
| AC-STATE-03 | 在迁移任一步骤注入失败 | 当前事务回滚；应用拒绝清空数据后继续运行；用户可看到失败和恢复升级前备份的路径 |
| AC-STATE-04 | 用旧版应用打开更高版本数据库 | 旧版拒绝写入，不覆盖或降级新数据库；用户可恢复升级前备份后再使用旧版 |
| AC-STATE-05 | 产生运行日志、复制技术详情或生成诊断导出 | 本地日志默认只保留最近七天；日志、错误、截图辅助和诊断包不含 API Key、完整请求、模型输出或完整服务地址；诊断导出只在用户主动触发后生成且不默认上传 |
| AC-STATE-06 | 应用启动或用户手动检查更新 | 启动后每天最多执行一次检查；检查不上传供应商目录、Key 或当前状态；发现更新只提示，下载和安装由用户确认，不静默安装 |
| AC-STATE-07 | 用户选择登录启动、关闭设置窗口或退出应用 | 登录启动默认关闭，首次使用时在当前页面询问；关闭设置窗口按确认后的托盘驻留行为隐藏而不是直接退出；只有托盘“退出 GPTEasy”结束进程 |
| AC-STATE-08 | 用户切换界面语言或主题 | 首次语言跟随操作系统语言且可切换简体中文/英语；主题可跟随系统、浅色或深色并立即生效；脚本语言跟随 Linux 导出时选择，不受窗口主题影响 |

## MVP Definition（锁定 v1 的交付边界）

### 完整首版必须包含

以下不是互相替代的候选项，而是同一个完整 v1 发布物的能力集合：

- [ ] 已验证供应商生命周期：标准字段、DayWay、不可变供应商 ID、模型获取、三项供应商验证、验证后保存、重新验证和删除保护。
- [ ] 原生 Codex 环境：检测桌面 Codex/本机 Codex CLI、代理 API 模式、原厂登录模式、外部配置、直接配置切换、备份/原子替换/失败恢复和待重启。
- [ ] Windows WSL2：发行版/默认用户检测、逐个切换、停止发行版临时启动并恢复、批量切换和逐项结果。
- [ ] Linux 切换脚本：全部已验证供应商、Bash 4+/Zsh 5+、导出警告、交互选择、GPTEasy 管理区块、目标配置备份、独立运行。
- [ ] 托盘优先设置 UI：供应商、WSL2、Linux 脚本、设置页面，首次使用、空状态、反馈、主题、语言和无障碍行为。
- [ ] 本地运行维护：SQLite 永久顺序迁移、脱敏诊断日志/导出、每日最多一次更新检查、用户控制的安装更新、登录启动和托盘驻留。
- [ ] Windows/macOS 目标平台和架构的发布验收，以及简体中文和英语。

### 实施中可以先做但不能作为正式交付

- [ ] 先用单一平台完成配置写入内核，再接入另一平台适配器。
- [ ] 先用一个已验证供应商贯通原生环境，再扩展目录更新、WSL2 和脚本。
- [ ] 先完成逐个 WSL2 切换，再加入批量结果模型。
- [ ] 先生成脚本并做静态检查，再做真实 Bash/Zsh 目标环境验收。

这些是风险控制顺序，不代表降低 v1 范围或发布不完整的中间版本。

## 需求定义时的实现复杂度焦点

1. **凭据在“可用性”和“脱敏”之间有两个同时成立的边界。** API Key 必须能明文保存、完整显示、复制并导出，但任何日志、错误正文、截图辅助和诊断导出都必须脱敏。验收应使用统一测试夹具覆盖所有输出通道。
2. **配置文件不是 GPTEasy 的全部状态。** 需要同时验证 SQLite 状态、Codex 磁盘配置、备份、运行中进程和 UI/托盘展示；任一层成功不能单独代表切换完成。
3. **供应商资料和环境引用必须分离。** 供应商目录保存供应商资料；环境只保存当前供应商 ID。更新资料时传播内容，改变环境选择时只改变环境引用。
4. **“立即重启”和“稍后重启”的语义必须先落成状态机。** 特别是桌面 Codex 与本机 Codex CLI 的进程发现、用户取消的写入前边界、立即重启失败后的恢复，以及稍后重启提示清除条件。
5. **WSL2 批量操作不是一个事务。** Windows 命令、发行版配置和发行版运行状态分别可能失败；结果必须逐项可见，并保留成功项和失败项的准确边界。
6. **Linux 脚本是可执行代码生成。** 供应商名称、服务地址、模型 ID 和 API Key 的 shell/TOML 转义、脚本自身语法检查、管理区块歧义停止和备份恢复需要专项测试，不能只测试普通 ASCII 示例。
7. **跨平台发布不是最后一次打包。** Windows/macOS 的默认路径、权限、进程发现、托盘行为、当前用户安装和更新流程应在对应平台的验收环境中闭环。

## 验收前仍需固定的实现参数（不改变锁定范围）

这些项目不是范围变更，而是把锁定行为变成可自动化/可重复验收时必须补齐的参数：

- 原生 Codex 配置的具体文件路径、字段映射、各平台版本差异和进程识别规则。
- “立即重启”对桌面 Codex 与本机 Codex CLI 各自的可执行动作、无法重新启动时的恢复状态和提示文案。
- WSL2 默认用户识别方法、发行版临时启动命令、停止状态恢复失败时的重试/恢复流程。
- Linux GPTEasy 管理区块的精确注释边界、允许修改的字段集合、Shell 基础命令清单和转义测试矩阵。
- 供应商验证中模型发现、Responses API 流式响应和工具调用闭环的请求最小集、超时、取消和错误分类。
- 供应商列表“较多时显示搜索”的确定阈值；UI 基线已经锁定要提供搜索，但尚未给出数字阈值。
- 更新检查的版本元数据来源、签名/完整性校验、下载失败和安装失败后的用户可恢复路径。
- 诊断脱敏规则的字段清单和测试夹具，尤其是地址中可能出现的凭据、错误嵌套结构和脚本生成错误。
